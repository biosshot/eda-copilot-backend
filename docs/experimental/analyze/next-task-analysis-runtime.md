# Следующее задание: исполнение анализа в отдельном процессе

Статус: задание после приёмки общего Node addon, 2026-10-21. Это один законченный инфраструктурный этап. Реализовать весь описанный путь и вернуть на проверку; к геометрии и физическим расчётам самостоятельно не переходить.

## Результат этапа

Из TypeScript можно отправить задачу импорта RoutingBoardV2 в отдельный процесс, получить исходный диагностический отчёт, отменить задачу или ограничить её время. Очередь ограничена, сбой worker не ломает родительский процесс, завершение backend освобождает дочерние процессы. Все восемь сохранённых плат запускаются через существующий launcher и этот путь. Работает также установленный npm-пакет.

Это ещё не расчёт физики. `imported: true` означает только успешный структурный импорт.

## Использовать существующее

- `native/node-addon/index.cjs` и его `importAnalysisBoard(json)` — единственная рабочая native-операция этого этапа. Не менять её семантику и отчёт.
- Имеющийся `workerpool`, отдельный **process worker**, подход из `src/pcb-layout/run-pcb-layout-pool.ts`, разрешение ресурсов через `backendResource`, существующую сборку worker entry points.
- Существующий `test:pcb-analyze` и его директории отдельных запусков.
- `disposeBackend` из `src/pcb.ts` расширить завершением analysis pool, сохранив завершение placement pool.

Перед добавлением helper искать готовый. Не создавать общую compute-runtime библиотеку и не рефакторить placement pool. Можно повторить небольшой специфичный код, если выделение общего модуля увеличивает область изменений.

## Внутренняя граница задачи

Создать `src/analyze`. Ориентир для внутреннего API (имена локальных файлов свободны):

```ts
type AnalysisProblem = Readonly<{
  kind: 'import-board';
  boardJson: string;
}>;

type AnalysisProgress = {
  jobId: string;
  phase: 'queued' | 'started' | 'completed' | 'failed' | 'cancelled';
};

type RunAnalysisOptions = {
  signal?: AbortSignal;
  timeoutMs?: number;
  onProgress?: (event: AnalysisProgress) => void | Promise<void>;
};

// Возвращаемый тип брать из деклараций analyze, не дублировать поля отчёта.
runAnalysisProblem(
  problem: AnalysisProblem,
  options?: RunAnalysisOptions,
): Promise<AnalysisImportReport>;
```

Это техническая граница исполнения, не изменение согласованного пользовательского DSL. Не добавлять публичный `/analyze` export пакета, builders или фиктивные будущие виды задач. При необходимости собрать внутренний entry point для package smoke test; не экспортировать его из root API.

`boardJson` копируется как строковое значение при отправке. `signal` и callback остаются в родительском процессе. В worker передаётся только сериализуемая задача. N-API загружается и вызывается внутри worker; импорт TS runtime не должен загружать addon в родительский процесс. Внутреннюю Rust Board наружу не возвращать и пока не удерживать между задачами.

## Поведение исполнения

1. Пул создаётся лениво. По умолчанию один worker и максимум четыре ожидающих задания; активные задания не входят в этот лимит. Допустить настройку числа процессов и размера очереди через существующий стиль environment configuration. Значения проверять; недопустимые значения не должны создавать неограниченный пул. Не вводить сложный планировщик.
2. На задачу действует конечный deadline, по умолчанию 30 минут. `timeoutMs` позволяет переопределить его положительным конечным значением. Время считается от принятия задания, **включая очередь**, и не обнуляется при запуске worker. Для дедлайна использовать монотонное измерение времени.
3. Разделять результат импорта и ошибки исполнения. Невалидная плата/JSON возвращает обычный отчёт с `imported: false` и diagnostics. Срыв исполнения отклоняет Promise с типизированным кодом: `ABORTED`, `TIMEOUT`, `QUEUE_FULL`, `WORKER_FAILED`, `DISPOSED` или `INVALID_REQUEST`. Не определять эти ситуации поиском текста в сообщениях для пользователя. Неизвестный `kind` и некорректные runtime-аргументы отвергать до native-вызова.
4. Уже отменённый signal не создаёт worker и не ставит задачу в очередь. Отмена ожидающего задания удаляет его и освобождает место. Отмена выполняющегося синхронного native-вызова требует остановки занятого процесса: сообщение в заблокированный event loop само по себе не обеспечивает отмену. Использовать возможности workerpool, проверить фактическое завершение процесса и ограничить ожидание остановки. Не останавливать соседние задания ради отмены одного.
5. При timeout действуют те же правила остановки/удаления. После crash, timeout или отмены пул способен выполнить следующую задачу. Сбойную задачу автоматически не повторять. Не возвращать поздний успешный результат после принятой отмены/таймаута.
6. Promise завершается ровно один раз. Удалять таймеры и AbortSignal listeners. Гонки завершения, отмены и dispose не создают зависшие Promise или unhandled rejection. Исключение/отклонённый Promise пользовательского progress callback не должно менять результат задачи или ломать очередь.
7. Прогресс содержит только реально наблюдаемые фазы, без выдуманных процентов. `started` приходит от готового worker перед native-вызовом. `completed` означает возвращённый отчёт, в том числе `imported: false`; это не утверждение об успешности физического анализа. Timeout и crash дают `failed`, отмена — `cancelled`. После терминального события новые события задания не доставлять.
8. Завершение analysis pool идемпотентно. При dispose отклонить ожидающие/активные задачи с `DISPOSED`, остановить процессы с конечным сроком и дождаться очистки. Во время завершения новые задачи отклонять; после завершившегося dispose следующий вызов может лениво создать новый pool. `disposeBackend` должен попытаться завершить оба пула даже при ошибке одного из них.

Очередь и число процессов ограничивают параллелизм и объём ожидающей работы, но **не являются жёстким лимитом native RAM**. Не выдавать V8 heap limit за лимит памяти Rust. Жёсткие ограничения RSS, глобальное распределение CPU между placement/analyze и повторное использование подготовленной геометрии оставить последующим этапам.

## Корпус плат и пакетирование

- Добавить `import.ts` в каждую из восьми существующих fixture-директорий. Общую логику держать в одном helper вне списка директорий плат, например `tests/helpers/pcb-analysis-import.ts`.
- Скрипт читает сохранённый V2 JSON, вызывает runtime и сохраняет полный отчёт в `PCB_ANALYZE_RUN_DIR/report.json`. При `imported: false` или ошибке исполнения завершает запуск ненулевым кодом. При диагностических `missing`/`limitation` без ошибки импорта не объявляет импорт неудачным. В `finally` освобождает runtime.
- Поддержать `npm run test:pcb-analyze -- --all --name import`. Не добавлять второй launcher и не создавать пустые `dc.ts`/`emi.ts`.
- Исходные JSON, native project files, export evidence и hashes не менять. Результаты запусков не превращать в эталон правильности физических расчётов.
- Включить worker и необходимые внутренние runtime-файлы в сборку/пакет. Проверить их работу из установленного tarball без доступа к исходникам репозитория, `tsx` и локальному старому binary. Расширить существующий package smoke test.
- Обновить README runtime/fixtures, документацию границ и CHANGELOG.

## Обязательные проверки

1. Все восемь реальных плат: отчёт через process worker совпадает целиком с прямым `importAnalysisBoard` — `imported`, counts, diagnostics, paths и source IDs. Отдельно malformed JSON и структурно невалидная плата возвращают диагностику, а не инфраструктурную ошибку.
2. Реальный addon вызывается в другом PID; родительский event loop остаётся доступным. В тестах должны быть и настоящий addon, и контролируемые test-only worker fixtures для гонок/аварий. Не добавлять production-флаги sleep/crash и не увеличивать реальные платы искусственно ради таймаута.
3. Проверить: очередь заполнена; отмена до отправки, в очереди и во время синхронной работы; timeout в очереди и во время работы; аварийный exit worker; следующая задача после каждого случая; освобождение места отменённым заданием.
4. Проверить два параллельных worker: остановка одного не завершает чужую задачу. Для зависаний/синхронной работы использовать управляемый test worker, события готовности и конечные watchdog deadlines; не полагаться только на короткие случайные sleeps.
5. Проверить гонку completion/cancel и dispose с активными/ожидающими задачами, повторный dispose, повторный запуск после него, исключения progress callback. Проверять отсутствие оставшихся дочерних процессов и unhandled rejection.
6. `npm run typecheck`, `npm run build`, focused runtime tests, launcher tests и запуск восьми `import` сценариев проходят. Новые native integration tests не пропускать из-за отсутствующего addon; сообщать о необходимости сборки и падать.
7. `npm run test:package` проверяет реальный analysis worker установленного пакета и сохранность прежнего placement worker; импорт работает при отключённом GPU. Проверки, зависящие от другой ОС или реального GPU, явно перечислить как не выполненные.

Если Rust не менялся, повторять полную Rust/placement benchmark серию не нужно. При необходимых изменениях загрузчика/сборки запустить соответствующие уже существующие focused проверки. Не ослаблять текущие проверки ради нового runtime.

## Что не входит

Никаких изменений RoutingBoardV2, экспортёра, анализа полноты CAD-геометрии, boolean/contacts/mesh/refill, физических solver, новых моделей, пользовательского DSL, кеша, handles/sessions, GPU, F32/F64-политики, UI или сетевых сервисов. Не переносить подготовку всего будущего pipeline в этот этап.

После приёмки runtime следующим функциональным блоком будет нормализация физической меди и электрическая связность с геометрическими эталонами, а затем первый DC solver. Точное задание на них выдаётся отдельно.

## Что вернуть валидатору

Список изменённых файлов, короткую схему parent → queue → process → addon, подтверждённую семантику deadline/cancel/dispose, команды и результаты тестов, пути к восьми отчётам, результаты installed-package smoke и известные ограничения. Не коммитить и не переходить к следующему этапу до приёмки.
