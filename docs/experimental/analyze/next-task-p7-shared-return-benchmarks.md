# P7: независимые эталоны общей земли и связанных каналов

Статус: параллельная работа над проверками, 2026-10-31.

Цель — подготовить и выполнить проверяемую приёмку прототипа из next-task-p7-shared-return-prototype.md. Это разработка fixtures, harness и эталонных данных, не преждевременное ревью агента и не изменение производственного solver.

## Владение

Агент benchmarks владеет tests/fixtures/analysis-shared-return-prototype/, scripts/verify-p7-shared-return-prototype.ts, tests/analyze-shared-return-benchmark.test.ts и docs/experimental/analyze/p7-shared-return-benchmark-results.md. Не менять файлы formulation, текущие сценарии и эталоны, production src/native, зависимости, CHANGELOG/implementation-plan. Прочитать AGENTS.md, CHANGELOG и два последних route/oriented результатов. Не коммитить и не удалять пользовательские файлы; не запускать субагентов.

## Работа

1. По первичным источникам из соседнего задания и другим найденным научным/официальным публикациям выбрать независимые проверяемые controls: широкая плоскость, край, разрыв, несколько плоскостей, сигнальный/возвратный переход, две связанные линии с общей узкой землёй. У каждого — исходная геометрия, материалы, порты, reference planes, termination, полоса, эталон, происхождение и известная неопределённость. Если полных данных нет, не выдумывать размеры/материалы и не называть кейс воспроизведённым измерением.
2. Простые аналитические controls дополнять сохранёнными converged whole-volume references/доступными опубликованными численными или лабораторными данными. Собственный прежний solver — регрессионный независимый путь, но не лабораторный эталон. Не ставить задачу установки внешних коммерческих/обязательных production solvers. Не выдавать совпадение двух одинаковых формул за независимую проверку.
3. Согласовать с formulation JSON manifest и output до реализации harness. Задать метрики до просмотра результатов: Z/задержка/передача/наводки/возвратный ток; относительные и абсолютные допуски, floors и их обоснование. Ориентиры <=8% основного, <=15% явно приближённого результата, без универсальной гарантии. Проверять диапазон целиком выбранными частотами/holdouts, не одну удачную точку; low-band и HF учитывать отдельно.
4. Создать harness с машинной таблицей pass/fail/unavailable, не исключать проваленные cases из итога. Проверки harness должны ловить изменение единиц, портов и нарушение допуска. Сформировать графики геометрии и сравнения, просмотреть их.
5. Выбрать из имеющегося корпуса реальные 2/4/6-слойные платы и каналы, подтвердить число слоёв/геометрию из данных, сохранить manifest выбора. Оценить возможность независимого сравнения и формат интеграционной проверки. Не подменять целый канал маленьким фрагментом без маркировки.
6. Когда prototype готов, запустить harness и сохранить наблюдаемые результаты. Не ждать бесконечно: если ещё не готов, отдать готовые эталоны/команды и пометить сравнение pending. Агент formulation может использовать harness самостоятельно.

Тяжёлые запуски только после малых контролей, одна задача одновременно, координация с formulation сообщениями. Лимиты и правила повторов как в соседнем задании: 8 GiB/600 s максимум на попытку при достаточном headroom, без автоматического расширения. Использовать сохранённые пригодные данные. Считать peak RSS/private commit и время всего процесса, отдельно численные стадии; не сравнивать failure latency с успешным solve.

Итог: runnable harness, source-bound fixtures/references, таблица покрытия/точности/ресурсов, конкретные пробелы. Не объявлять P7 закрытым. Если независимые данные для случая недоступны, прямо обозначить это и минимальный способ их получить. Не менять production под тесты и не ослаблять исходные guards.
