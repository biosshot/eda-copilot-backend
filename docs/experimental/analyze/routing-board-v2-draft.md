# RoutingBoardV2: черновик расширений для обсуждения

Дата: **2026-10-19**. **Рабочая структура из TypeScript-заметки предварительно зафиксирована пользователем; требует перепроверки. Только документация.** Широкие расширения и варианты из этой заметки не становятся автоматически утверждённым API. Типы, экспорт, router и анализаторы не изменяются. Основание: [аудит геометрии и экспорта](geometry-export-audit.md), [каталог анализов](analysis-catalog.md), [предыдущее обсуждение](routing-board-audit.md).

После уточнения пользователя подготовлены [читаемая структура TypeScript](routing-board-v2-shape.md) и [полный JSON-пример](routing-board-v2-example.json). Они показывают минимальное расширение. Новых типов кривых не вводим: дуги аппроксимируются точками. Ниже сохранён более широкий перечень потребностей для дальнейшего обсуждения, а не обязательный список новых полей.

## 1. Почему версия V2

Рекомендуется развивать RoutingBoard как одну общую модель с рабочим именем расширенного типа `RoutingBoardV2`. По уточнению пользователя поля `schemaVersion` и `importInfo` в плату не включаются. Существующий RoutingBoard и его экспорт пока оставить router без изменений. Это предложение по миграции, а не решение создать независимую модель анализатора навсегда.

Добавить к старому результату только `filledPolygons` недостаточно: импорт уже теряет отверстия, вид зоны, свойства переходов и точную геометрию некоторых площадок. Дополнять данные можно, но из исходного JSON/native API, до потери информации, с явным сопоставлением объектов.

Переиспользуем `PointMm`, `PolygonMm`, формы площадок, структуру слоёв/сетей, имеющиеся routing rules и stackup. Меняем только поля с недостаточной семантикой. При изменении типа поля нужна композиция через `Omit`/новую декларацию, а не притворная совместимость `extends RoutingBoard`. TypeScript structural compatibility не делает V2 безопасным входом старого Rust/router runtime.

Будущий путь: V1 остаётся у router → V2 появляется в backend с зафиксированной исходной ревизией → router мигрирует на общий контракт. До миграции V2 нельзя напрямую отдавать старому потребителю. Возможная V2→V1 проекция обязана перечислять потери и отказывать там, где результат изменит смысл задачи. Копирование типов и разработка конвертеров сейчас не выполняются.

## 2. Карта расширений

| Место | Предлагаемое изменение |
| --- | --- |
| Корень | Прежние поля платы с локальными расширениями; diagnostics возвращает операция импорта |
| `outline`, `cutouts` | Существующие точки с контролируемой аппроксимацией дуг; при нескольких телах — явная будущая поддержка или отказ, не выбор самого большого |
| `layers` | Стабильный ключ и физический порядок; mapping к native ID в source metadata; не путать порядок с числом слоя EasyEDA |
| `components` | Native ID, `footprintName`, при наличии отдельный распознанный `packageName`, размеры приближённого тела и их происхождение |
| `pads` | Обязательный ID в снимке, необязательный владелец для standalone pad; сохранённые отверстия; optional послойная геометрия |
| `copper.*.tracks` | Существующие points и widthMm; дуги аппроксимирует адаптер; при необходимости нестандартная медь нормализуется в постоянные области |
| `copper.*.vias` | Реальный span/type; existing размеры + provenance; детализация plating/padstack/backdrill по выбранным физическим моделям |
| `copper.*.zones` | Discriminated union `kind: 'pour' | 'fill'`, описанный ниже |
| `holes` | Отдельные сверления/пазы без владельца pad/via, включая NPTH; отверстие владельца хранится у него, без второй физической копии |
| `keepouts`, локальные rules | Реальные запреты по виду объекта/слоям; отдельные constraint regions и их scope, если присутствуют |
| `rules` | Сохранить routing rules; добавить таблицу effective refill presets/scopes, не сводить её к одному clearance |
| `stackup` | Переиспользовать RoutingStackup; расширять materials/локальную структуру под конкретные анализы; источник может быть DSL |
| Работа адаптера | Сохранение исходных IDs, преобразование координат и диагностика неизвестных свойств; отдельный importInfo внутри платы не добавляется |

`copper.fixed/editable` сохранить как право редактирования для routing job. Эти корзины **не определяют** Pour/Fill, источник меди или пригодность для физического расчёта. Анализ текущей платы учитывает обе корзины.

## 3. Геометрия меди

По уточнению пользователя сохраняем нынешнюю геометрическую модель. Аппроксимация выполняется адаптером, до передачи платы потребителю.

- Дорожка содержит прежние `points[]` и `widthMm`; дуговые участки превращаются в короткие сегменты.
- Область — существующий `PolygonMm` с `outer` и `holes`. Несколько островков — массив `PolygonMm[]`. Дуги и окружности сложных контуров тоже превращаются в точки.
- Для площадок сохраняются уже имеющиеся circle/rect/round-rect/oval/polygon. Дополнительного варианта с криволинейной границей не вводим.
- У дорожки одна ширина на объект, как сейчас; разные ширины уже выражаются разными дорожками. Для taper, teardrop или иной нестандартной меди нужна фактическая область, а не выдуманная средняя ширина. Связь с исходным track сохраняется, одна и та же медь не считается дважды.
- Текст и графика на медных слоях тоже могут быть проводящими областями. Их можно нормализовать в постоянный Fill с source kind; нельзя просто выбросить из-за отсутствия net или непривычного CAD-типа.

Авторитетная геометрия объекта — его представление существующими точками или примитивами площадок. Исходные CAD-команды могут оставаться внутренними данными адаптера; потребители не обязаны декодировать их повторно. Формат не содержит расчётную сетку решателя.

Для аппроксимации нужны метод, максимальное отклонение границы в mm, направление смещения (`inside`, `outside`, `mixed`), источник и сведения о неразобранных фрагментах. `0.001 mm` существующего router не утверждается универсально достаточным допуском для всех анализов. Кроме ошибки границы требуется контроль сохранения отверстий и контактов: малая ошибка может замкнуть узкий зазор. Увеличенный obstacle pad из V1 нельзя выдавать за exact copper.

Перед реализацией закрепить одну систему координат, направления углов и преобразование bottom-side. Предлагается сохранить frame нынешнего RoutingBoard, а CAD→board transform записывать явно; все board-level контуры находятся в этом frame, pad-local формы проходят ровно один transform. mm остаются общей единицей длины. Численная политика F32 существующего PCB-кода этим черновиком не меняется.

## 4. Pour, Fill и реальная заливка

Актуальный эскиз типов приведён [отдельно](routing-board-v2-shape.md). Обоим видам зоны добавляем `kind` и `filledPolygons` с послойными статусами и массивами существующего `PolygonMm`. В отличие от предыдущего эскиза, разные имена `cadFillByLayer` и `copperByLayer` не требуются.

**Источник фактической меди Pour — native `PrimitivePoured.getState_PourFills()` из EasyEDA.** `PrimitivePour` даёт исходное описание и параметры, `PrimitiveFill` — постоянную медь. Чтение native API, уже используемое для RawPcb, переносится в экспорт общей модели.

Инварианты предлагаемой модели:

1. Известное назначение сети переносится в `net`. Неизвестная сеть не означает отсутствие меди. Различие подтверждённого no-net и неудачного чтения при необходимости фиксируется в metadata импорта; отдельный обязательный netState в минимальном эскизе пока не вводится.
2. Для каждого слоя из `layers` присутствует запись состояния; посторонние ключи запрещены. Это позволяет хранить общий multilayer объект без потери послойных результатов.
3. Pour outline описывает область заливки, но сам не входит в физическую медь. Физическую медь дают только выбранные filled areas.
4. Fill содержит постоянную физическую медь. Нативный outline/stroke/hatch нормализуется с учётом fill mode, line width, caps/joins и правил отверстий. `fill: false` у Poured fragment не является автоматически отрицательной полярностью: сначала декодируется его действительный смысл.
5. `available` с `polygons: []` — прочитанный пустой результат. Он отличается от `missing`/`failed` и сам по себе не запускает refill.
6. `nativePrimitiveIds` сохраняет IDs Poured/фрагментов. После boolean union одному участку могут соответствовать несколько исходных фрагментов.
7. `current` ставится только при подтверждении актуальности CAD-результата. Чтение в текущий момент или hash экспортированного контура сами по себе этого не доказывают.
8. Если в legacy `fillRegions` нельзя определить Pour/Fill, адаптер не выбирает вид наугад. Нужны native evidence либо запись неразобранного объекта и неполное покрытие. Анализ, зависящий от этой меди, не получает статус полной модели.
9. Перекрытия track/pad/Fill/заливки на одном физическом слое не создают несколько толщин меди. При построении расчётной области нужна геометрическая нормализация с сохранением принадлежности исходным объектам; соприкосновение разных назначенных сетей остаётся short, а не исчезает при объединении.

Предлагаемое место оригинальной заливки — **внутри соответствующей зоны**, в `filledPolygons`. Так не возникает отдельного независимого массива меди, который легко посчитать ещё раз. Значение `kind` различает перестраиваемый Pour и постоянный Fill.

Результат собственного refill предлагается хранить **в производных данных запуска анализа**: board snapshot/hash, zone ID, layer, geometry, engine/version, effective rules hash, зависимости и предупреждения. Он не перезаписывает CAD `filledPolygons` и не применяется в CAD. Выбор «CAD либо рассчитанный результат» выполняется один раз при построении физической модели.

## 5. Что нужно для fallback-refill

Нормализованное описание собирается из прежних полей `RoutedZone` и дополнительных presets в `board.rules.refill`, на которые ссылается `refillRules.ruleSetId`. Так не копируем большие таблицы на каждую зону. Сырые EasyEDA presets могут сохраняться как source evidence: ядро не должно требовать произвольный native JSON вместо определённых правил.

| Группа правил | Что необходимо выразить/проверить |
| --- | --- |
| Приоритет и взаимодействие | priority, правило при равенстве, порядок обработки, overlaps same-net/different-net, поведение по отношению к постоянному Fill |
| Область применения | слой, zone/net/class, локальные constraint regions, происхождение и порядок overrides; не предполагать наследование по догадке |
| Зазоры | zone↔track/pad/via/zone, разные сети и особые same-net случаи, board edge/cutout/hole/keepout; разрешённая матрица либо эквивалентные явные правила |
| Подключение | solid/thermal/none; разные настройки SMD/TH/via; overrides конкретной площадки, ширина/зазор/угол/число spokes и применимые исключения |
| Заполнение | solid/hatch, ширина/шаг/ориентация и привязка сетки hatch, граничная полоса, минимальная ширина/шейки и сглаживание, если исходный режим это использует |
| Островки | preserve/remove, критерий связанности, порог площади, учёт подключений через pads/vias; `preserveSilos` не сводить к произвольному порогу площади |
| Геометрическая политика | clip к телу платы/вырезам, обработка самопересечений, допуски, разрешение конфликтов, неподдерживаемые режимы |

Это список потребностей движка, **не утверждение, что EasyEDA уже экспортирует каждое поле**. Сначала установить native значения и семантику. Если число spokes или tie-break неизвестны, не выдавать придуманное значение за CAD-настройку. `complete` означает полноту декодирования применимой постановки; поддержку конкретным refill engine нужно проверять отдельно.

Порядок fallback:

1. Проверить полноту геометрии окружения: контуры, все препятствия и медь, слои, отверстия, площадки и взаимодействующие Pour. Нельзя корректно пересчитать одну зону, игнорируя зоны с большим приоритетом.
2. Если CAD fill прочитан и пригоден, использовать его. Физический дефект (short, оборванный thermal) является результатом анализа, а не основанием автоматически «исправить» плату.
3. При missing/failed/unsupported либо явно выбранном анализе stale fill проверить доступность исходного контура, правил и поддержку режима движком. Политика выбора задаётся сценарием DSL, а не скрытой эвристикой board importer.
4. При достаточных данных построить согласованный набор заливок с зависимостями и приоритетами. Пометить результат как расчётную реконструкцию; совпадение с CAD требует отдельной проверки.
5. При недостатке данных вернуть конкретные причины и ограничить зависящие анализы. Пользователь может явно задать приближение в сценарии; оно фиксируется как допущение, а не как исходное состояние платы.

Для Fill такого fallback нет: его геометрия задана напрямую. Можно поддержать другой декодер той же формы, но нельзя заменить её результатом заливки по чужим правилам.

## 6. Остальные физические данные

**Pads и отверстия.** Существующий `hole` уже описывает round/slot, offsets, rotation и plated. Нужно прежде всего его надёжно заполнить. Для различающихся слоёв — optional per-layer shapes с однозначным правилом замещения общей формы. Для нестандартного span/металлизации — явные данные, а не предположение сквозного подключения. Независимые NPTH/slots не выводятся из keepouts. Размер сверла и готового отверстия нужно различать, если источник даёт оба; неизвестный смысл размера фиксируется.

**Vias.** Существующие диаметры, from/to layers и type сохраняются. Необходимые для конкретного расчёта данные: реальная длина через stackup, толщина металлизации и проводимость. Общая `stackup.viaPlatingThicknessUm` уже есть. Индивидуальные overrides, removed pads, backdrill, fill/cap и сложные padstacks добавляются по поддерживаемой модели; отсутствие поддержки обнаруженного случая явно ограничивает расчёт. Backdrill глубина может находиться между слоями, одного from/to для неё недостаточно.

**Stackup и материалы.** Начальный физический stackup может задаваться DSL. Источник и допущения сохраняются; валидируется соответствие copper layers. Для дальнейших моделей нужны conductivity и её температурная зависимость; εr/tanδ и частотные зависимости, roughness; thermal conductivity, density, heat capacity. Material ref не заменяет отсутствующее свойство. Локальные stackups, rigid-flex, cavities и неоднородные среды — будущие расширения; V2 не объявляет их поддержанными одним optional полем.

**Компоненты.** `footprintName` полезен уже сейчас, но библиотечное имя не всегда однозначно задаёт корпус. При распознавании стандартного варианта можно строить приблизительное внешнее тело с dimensions/provenance. CAD 3D-модели пока не импортируются. Внутренние thermal paths, электрическая модель, мощность и коэффициенты охлаждения не выводятся из имени корпуса. Terminal mapping связывает модели с реальными pad IDs, включая несколько площадок одного вывода.

**Связность.** Net — проектное назначение, а не доказательство контакта. Физическая связность строится по меди и металлизации; shorts между разными net сохраняются для диагностики. `connectedPadIds` V1 можно сохранить как native evidence, но это не замена геометрии. Net ties также требуют явного намерения, а не автоматического объединения сетей по касанию.

## 7. Проверки адаптера и диагностика вне платы

После уточнения пользователя не вводим в RoutingBoard отдельные `importInfo`, `coverage` или `source`. Ниже — возможные проверки и сведения в diagnostics операции/отладочном отчёте, не обязательные поля board-контракта. По семействам (`boundary`, `pads`, `tracks`, `vias`, `holes`, `pourDefinitions`, `pouredCopper`, `fills`, `copperGraphics`, `keepouts`, `rules`, `stackup`) полезно проверять:

- Состояние `complete | partial | unavailable | not-requested`, источник и diagnostics.
- Число увиденных, импортированных и пропущенных объектов, когда исходный API позволяет их установить; неизвестное количество не равно нулю.
- Перечень неподдержанных видов/свойств и конкретных объектов.
- Отдельно качество представления: exact относительно исходного CAD-описания, approximated или unknown. Полное перечисление объектов не означает точную геометрию.

Контекст документа, момент чтения и параметры преобразования координат может учитывать адаптер/операция. Native IDs сохраняются в контексте документа; при их отсутствии ID уникален в текущей плате, без обещания стабильности между экспортами. Designator и координаты не используются как универсальная идентичность.

Если autoroute JSON, DRC и native Poured читаются разными запросами, нужно проверять согласованность доступным механизмом; при невозможности проверки операция сообщает ограничение. Timestamps сами по себе не доказывают атомарность. Ошибки API не заменяются пустыми массивами без диагностики. Orphan Poured не получает выдуманный TOP layer.

Runtime preflight каждого анализа проверяет **свои** требования. Например, отсутствие теплового материала не мешает измерить длину, но недостающая медь мешает утверждать корректность DC PI. Отсутствие поддерживаемого объекта не равно отсутствию дефекта. Hash снимка нужен для воспроизводимости и cache invalidation; он не доказывает физическую точность или свежесть заливки.

## 8. Проверка против каталога анализов

«Все необходимые входы» относятся к сочетанию **платы + моделей + сценария**. RoutingBoard не должен превращаться в контейнер частот, тестовых стимулов и всех внешних объектов. Ниже покрытие требований, а не обещание поддержки решателями.

| Анализы | В расширенной плате | Отдельные модели/сценарий |
| --- | --- | --- |
| A01 preflight | Полная медь, layers, pad IDs, intended nets, геометрическая точность, правила | Опорные сети, endpoints, требования, при необходимости фронты |
| A02–A03 линии/сечения | Геометрия проводников, stackup, mask/materials | Выбранное сечение, частота, boundary conditions; standalone калькулятор может обойтись без board |
| A04–A05 DC | Медь/отверстия/металлизация, толщины, проводимость, terminals | Источники, нагрузки, контакты, температура и возврат |
| A06–A07 PI/PDN | Топология, planes/vias, materials, mapping terminals | VRM/decap модели, порты с возвратом, токи/частоты/время, начальные условия |
| A08–A11 SI/crosstalk/multiport/DDR | Кривые/ширины/зазоры, reference copper, stackup, vias, terminal mapping | IBIS/Touchstone и иные выбранные модели, Tx/Rx, stimuli, ports/reference planes, timing |
| A12–A14 thermal/electrothermal | Слои/медь/отверстия, материалы, положение и оценочные размеры корпусов | Мощности, package thermal model, контакты/TIM, охлаждение, временные условия |
| A15 паразитные RLC | Полная геометрия контура и возврата, материалы, переходы | Ports, частоты, переключающие модели |
| A16–A17 RF/EM/EMC | Поддерживаемая геометрия платы и проводников | Дополнительная 3D-сцена, разъёмы/кабели/экраны, возбуждения и границы; одной V2 платы недостаточно |
| A18 аналоговые схемы | Связь terminals и извлечённые паразитики | Схемный netlist, нелинейные модели и стимулы; не дублировать схему в RoutingBoard |
| A19 механика | Контур, слои, точки размещения как основа | Полная сборка, крепления, механические материалы и нагрузки; вне текущего 3D-охвата |
| A20 ERC/DFM/изоляция | Геометрия, holes/pads, masks/paste при выбранных проверках, rules | Роли/рейтинги компонентов, производственные и эксплуатационные требования |
| A21 силовые расчёты | PCB-пути и terminal mapping при board-level расчёте | Топология преобразователя, магнитные элементы, рабочие режимы и модели потерь |
| A22 sweep/подбор/статистика | Стабильные ссылки на параметризуемые объекты и исходный снимок | Диапазоны, распределения, корреляции и цели; варианты не изменяют исходную CAD-медь |

Таким образом, для широкого первого набора критичны не только зоны: контур/вырезы, отверстия и plating, физические слои, материалы, идентичность и отчёт о полноте. Masks/paste, advanced padstacks, локальные stackups и внешняя 3D-сцена должны иметь явные границы поддержки. Нельзя сейчас доказать универсальную полноту для всех будущих анализов; можно проследить каждый известный запрос до его данных и не скрывать пробелы.

## 9. Что требуется решить дальше

1. При итоговом пересмотре перепроверить предварительно зафиксированную структуру V2 и миграцию на общую модель после переноса router.
2. Уточнить координатные соглашения и допуски аппроксимации в существующих points/PolygonMm; типы кривых по уточнению пользователя не вводятся.
3. Проверить native export на контрольных случаях из [аудита](geometry-export-audit.md), особенно Fill mode, hole/plating, layer spans, inheritance и freshness.
4. Утвердить минимальные поля/поддерживаемые случаи для каждого выбранного анализа и правила допуска неполных данных.

После итоговой перепроверки всего плана можно утверждать runtime schema, Rust/TS представления и миграцию. Рабочая структура из TypeScript-заметки предварительно зафиксирована; остальные расширения этой заметки остаются кандидатами.
