# Анализаторы: рабочие материалы обсуждения

**Геометрический блок P4 принят 2026-10-22, R1/R2 закрыты:** [независимая приёмка](copper-geometry-review-2026-10-22.md), [границы, точность и результаты](copper-geometry-verification.md).
Следующее задание: [сетка слоистой проводимости и физический профиль](next-task-conduction-mesh.md).
Операция `prepare-geometry` использует тот же process runtime; восемь сценариев
`geometry.ts` сохраняют JSON/SVG. Ниже сохранены исторические договорённости;
meshing, refill и физические решатели в этом этапе не реализуются.

Дата начала: **2026-10-19**. Текущий статус: **структурный импорт, общий addon, process runtime и подготовка геометрии приняты; физические расчёты ещё не реализованы**. Договорённости ниже сохраняют историю обсуждения; фактическая реализация описана в ссылках выше.

Текущие фактические границы: [Rust-импортёр](../../../native/analyze/README.md), [общий addon](../../../native/node-addon/README.md), [process runtime](../../../src/analyze/README.md) и [проверки исполнения](analysis-runtime-verification.md). Восемь сохранённых плат запускаются через `test:pcb-analyze -- --all --name import`. Успешный импорт не подтверждает физическую полноту экспорта и не заменяет запланированный аудит корпуса.

**Рабочая структура RoutingBoardV2 принята.** Можно переходить к P0–P2: уточнить соглашения экспорта, реализовать отдельный V2-путь и проверить корпус плат. Обязательных новых архитектурных обсуждений перед этим этапом нет. Полнота для всех анализов не объявляется доказанной; корректировки следуют из реальных ограничений экспорта и моделей. В этой итерации изменена только документация.

**2026-10-20: базовый DSL согласован.** Приняты привязки моделей, timing, локальные a.model и измерения. Отдельный механизм контроля границ/двойного учёта моделей отклонён. Далее — формализация и архитектура реализации; DSL меняется при обнаружении конкретных ограничений.

**2026-10-21: согласованы математическая основа и структура реализации.** Слоистый FEM для DC/thermal, MNA, гибридное извлечение, приоритет планарного MoM, сокращение моделей и повторное использование: [методы и ограничения](numerical-architecture.md). Выбран **многопоточный CPU сейчас, GPU — будущее расширение**. [Структура и этапы](implementation-structure.md): две Rust-библиотеки, общая оболочка N-API и один `.node`; compute-runtime заранее не создаём. Приняты faer/rayon, проверка spade на реальной меди и rustfft по потребности. Математические расчёты выполняем в F64 по умолчанию; раннее сравнение с F32 отменено. F32 и GPU остаются будущими возможностями. Передача проблемы и управление выполнением — по концепции packer; первый этап — аудит и тестовый корпус не менее 20 плат. Правила F32 packer сохраняются.

Здесь постепенно собираются договорённости, варианты и исследовательские материалы по анализаторам EDA Copilot. Документы не являются спецификацией реализованного API, обязательством по составу релиза или поручением начать разработку.

**Подготовлен подробный [план P0–P15](implementation-plan.md):** сначала экспорт/корпус и аудит, затем инфраструктура/геометрия/DC, электрическое ядро/извлечение/PI и остальные согласованные методы. [Проверка достаточности V2](routing-board-v2-sufficiency.md) выявила конкретные пробелы G1–G7; универсальная полнота текущего черновика не подтверждена. Это статическая проверка кода и трёх сохранённых JSON, а не выполненный аудит 20 плат.

В [текущей TypeScript-форме V2](routing-board-v2-shape.md) сохранены PartUuid/значение экземпляра, формы площадок по слоям, inline правила заливки внутри Pour и native заливки (без pad.zoneConnection). Неподтверждённые расширения маски/via/refill вынесены в будущее; они не наследуются скрыто через тип зоны. Полный fallback-refill остаётся задачей плана и требует расширения контракта после аудита. Согласованные stackup и размеры корпусов из DSL/каталога сохраняются.

## Метод проверки полноты контракта

1. Составить широкий каталог пользовательских задач, включая будущие направления.
2. Для каждого выбранного анализа описать конкретную поддерживаемую модель и ожидаемый результат.
3. Выписать необходимые геометрические данные, материалы, компонентные модели, возбуждения и граничные условия.
4. Указать происхождение каждого входа: CAD, библиотека, пользователь, измерение или явно разрешённое приближение.
5. Проверить эти потребности на корпусе не менее 20 разнообразных плат; дополнить малыми аналитическими задачами и расчётами без платы.
6. После этого обсуждать контракт и окончательную архитектуру.

Список необходимых данных в каталоге — материал для этого процесса, **не схема `Board`**. Желание предусмотреть будущее не означает, что каждый простой расчёт должен требовать все возможные данные. Некоторые входы вообще не являются свойствами платы: например, фронт драйвера, токовая нагрузка, температура среды или модель вентилятора.

## Что считать достоверным анализом — предложение для обсуждения

Опубликованные алгоритмы существенно облегчают разработку. Однако формула ещё не определяет корректное извлечение геометрии, выбор опорных проводников, дискретизацию, контакты, граничные условия и область применимости. Контракт — одна из главных задач, но не единственный источник сложности.

Предлагается для каждого анализа иметь:

- область применимости и явно перечисленные упрощения;
- эталонные задачи и критерии численной проверки;
- объяснимые результаты, единицы и происхождение параметров;
- различие между отсутствием данных, ошибкой вычисления и нарушением требования;
- воспроизводимый сценарий для человека и LLM.

Это критерии для обсуждения, а не утверждённый контракт результатов. Наличие более сложного численного метода само по себе не означает более достоверный ответ.

## Как обновлять эти документы

- Явно отличать договорённость пользователя от предложения и подтверждённой внешней возможности.
- Не превращать пример из переписки в публичную спецификацию.
- Для нового анализа дописывать результаты, входы, ограничения и способ проверки.
- При выборе состава версии переводить конкретные пункты каталога из кандидатов в согласованный набор с датой решения.
- Ссылки на продукты подтверждают существование класса задач, но не доказывают точность нашей будущей реализации.
