# RoutingBoard: текущий экспорт и обсуждаемые расширения

Дата: **2026-10-19**. Основание: чтение локального кода, без запуска CAD и без проверки нового экспорта на живой плате. [Общий контекст](README.md).

Продолжение обсуждения: [проверка геометрии и сохранённых JSON](geometry-export-audit.md), [конкретный черновик RoutingBoardV2](routing-board-v2-draft.md). Они уточняют предложения ниже, но не утверждают окончательную схему.

## Выбранная основа и открытые предложения

Пользователь выбрал **RoutingBoard основной моделью**, которую нужно дополнять вместо создания параллельного типа платы. Конкретные поля и итоговая схема ещё не утверждены.

Пользователь предложил: использовать реальную медь EasyEDA по существующему пути RawPcb; рассмотреть собственный refill при отсутствии/непригодности заливки; задавать недоступный физический stackup через DSL; временно скопировать типы из router в backend с учётом возможного будущего переноса router. Ассистент поддерживает направления с оговорками ниже. Это документация обсуждения, не поручение реализовать или копировать код сейчас.

## Что делает RawPcb

Источник: [getPcbRaw](../../../../easyeda-copilot/extension/src/eda/pcb.ts), функция начинается около строки 686; [типы RawPcb](../../../../easyeda-copilot/shared/types/pcb/raw.ts).

| Объект EasyEDA | Действие текущего кода | Что попадает в RawPcb |
| --- | --- | --- |
| `PrimitivePour` | Получает объекты и строит `pourById` | Самостоятельное описание контура/правил Pour не возвращается; объект используется для получения net/layer его Poured |
| `PrimitivePoured` | Через `getState_PourPrimitiveId()` находит Pour; читает `getState_PourFills()` и пути | Реальные фрагменты заполнения в `polygons`: `sources`, `fill`, `lineWidth`, `net`, `layer` |
| `PrimitiveFill` | Читает `getState_ComplexPolygon().getSource()` | Постоянная область в том же `polygons`, с `fill: true` и `lineWidth: 0` |

Таким образом, пользователь прав: существующий RawPcb уже получает результат заливки EasyEDA, а не рассчитывает его сам.

Ограничения текущего представления для физического анализа:

- В общем массиве не сохраняется различие Poured/Fill и связь фрагмента с исходным Pour.
- Для полигонов не сохраняются исходные primitive ID.
- `fill` — признак заполнения фрагмента, а не признак «объект является PrimitiveFill». Для незаполненного пути важна `lineWidth`.
- Некоторые ошибки чтения превращаются через `catch(() => [])` в пустые массивы. Отсутствие данных нельзя автоматически считать отсутствием меди.
- При отсутствии родительского Pour текущий код назначает фрагменту пустую сеть и слой `TOP`; такой fallback неприемлем как незаметное физическое допущение анализатора.
- Код не доказывает актуальность и полноту результата заливки. Для анализа потребуется отдельно обозначать эти состояния.

Переиспользовать следует путь извлечения реальной геометрии, сохранив её происхождение и убрав неоднозначность. Сам тип RawPcb не становится вторым главным контрактом.

## Что делает путь RoutingBoard

Источники: [exportRoutingInput](../../../../easyeda-copilot/extension/src/mcp-client.ts), [importedZones и importEasyEdaAutorouteJson](../../../../easyeda-copilot/mcp/src/routing/easyeda-autoroute-adapter.ts), [routing-operation](../../../../easyeda-copilot/mcp/src/routing/routing-operation.ts), [DRC merge](../../../../easyeda-copilot/mcp/src/routing/easyeda-drc-adapter.ts).

- Экспорт получает `getAutoRouteJsonFile()` и отдельно native DRC.
- `importedZones()` читает `root.fillRegions`, преобразует контур/отверстия и слои, переносит net/id при наличии и выставляет `connection: 'solid'`.
- Этот импортёр не читает `PrimitivePoured.getState_PourFills()` и не сохраняет явное различие перестраиваемой зоны и постоянной меди.
- При импорте здесь не заполняются priority, thermal-параметры, hatch и остальные подробные правила исходного Pour, хотя часть соответствующих полей существует в `RoutedZone`.
- DRC объединяется с routing rules; это не восстанавливает автоматически полную постановку заливки каждого Pour.
- Без проверки реальных файлов нельзя утверждать, каким именно исходным объектам соответствует каждый `fillRegions` во всех версиях EasyEDA.

Вывод: структура RoutingBoard подходит как основа, но текущий экспорт в неё не гарантирует все данные для точного воспроизведения заливки EasyEDA.

## Зоны и собственный refill — предложение

Сохранить в существующем описании зон различие между:

1. Перестраиваемым Pour: исходный контур, правила и доступный результат заполнения.
2. Постоянной областью Fill: заданная медь, которая не должна самопроизвольно обрезаться правилами refill как Pour.

Фрагменты Poured относятся к результату конкретного Pour, а не становятся независимой второй копией той же меди. На конкретный расчёт выбирается одно используемое заполнение зоны; исходная и пересчитанная версии не складываются.

Собственный refill полезен как восстановление расчётной модели, если есть пригодный исходный контур, необходимые правила и поддерживаемая семантика. Его результат нужно отличать от реально прочитанной меди CAD. Физически ошибочная, но корректно прочитанная заливка должна сначала анализироваться как есть: например, найденный short нельзя автоматически убрать пересчётом и затем объявить исходную плату исправной.

Пустая достоверная заливка не равна отсутствию данных. Ошибка декодирования формы не гарантирует, что получится восстановить её по контуру. При нехватке правил нужно сообщать ограничение модели, а не обещать совпадение с EasyEDA. Для постоянного Fill fallback-refill как для Pour не применяется.

Точные состояния, поля, размещение результата и режим выбора fallback ещё обсуждаются. `FilledZone` router описывает результат его собственного расчёта; использовать его как доказательство фактической меди EasyEDA не предлагается. Общую геометрию `PolygonMm` можно переиспользовать независимо от происхождения заполнения.

## Уточнения по остальным существующим типам

Источник: [contracts.ts router](../../../../copilot-router/src/core/contracts.ts).

- **Площадки:** `RoutingPad` — площадки выводов компонентов. Сейчас `shape` один на список `layers`. Обычные SMD и одинаковые площадки по слоям уже выражаются; послойные различия padstack — возможное расширение для конкретных будущих случаев, не обязательное усложнение V1. Наличие поля `hole` в типе не означает, что каждый существующий импортёр его заполняет.
- **Дорожки:** у одного `RoutedTrack` одна `widthMm`, путь — `points[]`; две точки уже описывают обычный сегмент. Разные объекты одной сети могут иметь разные ширины. Это не ограничение всей сети одной шириной. Предыдущая формулировка ассистента была слишком общей. Дуги и точность их аппроксимации — отдельный вопрос.
- **Vias:** уже есть диаметр площадки, диаметр отверстия, начальный/конечный слои и тип. `RoutingStackup` уже содержит общий `viaPlatingThicknessUm`. Для начального DC-расчёта сначала нужно заполнить имеющиеся физические данные. Индивидуальная металлизация, послойные площадки, backdrill/stub и via filling относятся к выбранным более подробным моделям и не объявлены обязательными полями V1.
- **Компоненты:** поддерживается предложение добавить обозначение корпуса, сохранив существующие компоненты. Схема полей ещё не утверждена.

## Stackup через DSL

Текущий `importEasyEdaAutorouteJson()` не устанавливает `board.stackup`. `getPcbStackLayers()` читает список/число слоёв, а не полный физический stackup. Обратное применение stackup в EasyEDA явно сообщает об изменении только числа медных слоёв. Это вывод о наших текущих путях кода, а не доказательство отсутствия любых API во всех версиях EasyEDA.

Предложение: использовать уже существующий `RoutingStackup`, заполняя необходимые параметры через Analysis DSL/профиль производителя. Не изобретать второй тип stackup только из-за другого источника данных. LLM может оформить известные параметры; неизвестные толщины и свойства нельзя выдавать за прочитанные из CAD. Проверять соответствие указанного stackup фактическим слоям платы.

Расширения свойств материалов добавлять под выбранные анализы, а не ради самого расширения. Отсутствие stackup не мешает всем геометрическим проверкам, но ограничивает зависящие от него физические расчёты.

## Идентификация — минимальное предложение

- Использовать существующие `id` для ссылок на объекты, не вводя новую глобальную систему идентификаторов без необходимости.
- Где CAD даёт primitive ID, сохранять его с контекстом документа. Для фрагментов заливки хранить связь с Pour/Fill.
- Если CAD-ID недоступен, назначать уникальный ID в пределах снимка и не обещать его стабильность между экспортами.
- Для привязки результатов к конкретной версии использовать идентичность снимка/ревизию; точное поле не выбрано.
- Индекс массива, координаты или имя сети не являются универсальным устойчивым ID объекта.
- Нынешний импортёр RoutingBoard использует для pads составной `designator:padKey`, для tracks/vias/zones — `id` из autoroute JSON при наличии. Это нужно учитывать при объединении с прямым экспортом RawPcb: одинаковые координаты сами по себе не доказывают идентичность.

## Временная копия типов в backend

Ассистент считает временную копию оправданной, если router планируется переносить в backend: это позволяет не создавать отдельный репозиторий контрактов и не подключать runtime router только ради модели.

Предлагаемые условия будущего переноса: сохранить имена/семантику базовых типов, записать исходную ревизию, перечислить локальные расширения, не копировать весь движок и не поддерживать бесконечно две независимо развивающиеся версии. После переноса router использовать одну общую декларацию. Одного TypeScript-типа недостаточно для проверки входов: runtime-валидация и Rust-декодирование должны учитывать те же расширения.

Сейчас создана только эта заметка. Типы, импортёры и алгоритмы не копировались и не изменялись.
