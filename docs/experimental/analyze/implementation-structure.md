# Структура реализации и порядок разработки

Дата: **2026-10-21**. **Согласовано пользователем; только документация, без реализации.** Дополняет [математическую архитектуру](numerical-architecture.md), не меняет [DSL](dsl-reference.md).

## 1. Две библиотеки и один Node addon

- PCB board packer становится Rust-библиотекой размещения.
- Анализатор — отдельная Rust-библиотека в `native/analyze`.
- Отдельный crate оболочки N-API зависит от обеих библиотек и собирается в один платформенный `.node`.
- Скрипт запускает Cargo для оболочки и упаковывает результат. Это не склейка двух заранее собранных `.node`.
- `native/compute-runtime` заранее **не создаём**. Общую библиотеку выделяем только при появлении конкретного кода, который действительно выгодно переиспользовать. Она может вообще не понадобиться.

```text
TypeScript backend
        │
        ▼
Оболочка N-API → один .node
        ├── pcb-board-packer: Rust-библиотека
        └── analyze: Rust-библиотека
```

Ядра не зависят друг от друга и от Node.js. Оболочка адаптирует вызовы, данные и ошибки; физика остаётся в библиотеках. Локальные Cargo path-зависимости не требуют нового репозитория, публикации crate или отдельной программы у пользователя. Имя и путь crate оболочки уточняются при формализации сборки.

Это решение заменяет прежнее предложение оставить packer общей N-API оболочкой. Будущая миграция выделяет оболочку из packer, сохраняя действующие экспорты, поведение placement, правила F32 и GPU размещения. Если используется Cargo workspace, корректно переносятся root-only profiles/patch, lockfile и пути сборки. Сейчас манифесты и исходники не изменяются.

## 2. Переиспользование по фактической потребности

| Существующая часть | Подход |
| --- | --- |
| Загрузка ресурсов и native, сборка/упаковка | Использовать с адаптацией общей оболочки |
| Ограничение CPU-параллелизма | Использовать принципы; код переносить только при совместимости |
| GPU-очередь, память и буферы | Источники опыта для будущего GPU, не обязательный перенос сейчас |
| Placement-кеш | Использовать принципы; физические модели имеют собственные ключи и жизненный цикл |
| Геометрические функции | Проверять соответствие реальной меди, контактам и точности |
| Scoring, поиск размещения, маршрутные эвристики | Оставить в placement |
| FEM, MNA, извлечение, MoM, сокращение моделей | Реализовать в анализаторе с выбранными численными библиотеками |

Аудит кода: `compute/cpu.rs` управляет разрешениями выполнения и ожидания, но не является универсальным пулом потоков. `compute/gpu.rs` связан с placement-геометрией, числовыми проверками и внутренними путями crate. Каталог compute целиком не считается независимой библиотекой. Переиспользование не является обязательным условием разработки анализатора.

## 3. Внутренние модули analyze

Это модули одного crate, а не отдельные библиотеки на каждый анализ.

| Модуль | Ответственность |
| --- | --- |
| input | Проверка и нормализация платы, stackup, материалов и моделей |
| geometry | Реальная медь, контакты, пространственные индексы |
| mesh | Расчётные сетки и перенос величин |
| numerics | Матрицы, решатели, интегрирование, комплексные операции |
| conduction | Электрическая проводимость и теплопроводность |
| extraction | Сечения, переходы, электрические параметры геометрии |
| network | MNA, частотная и временная электрическая динамика |
| em | Поля, планарный full-wave, излучение |
| reduction | Сокращение моделей и fitting |
| analyses | Композиция DC/thermal/SI/PI/EMI-расчётов |
| results | Сигналы, карты, измерения, timing, eye, диагностика |

Исполнение первоначально организовано внутри анализатора. Точные имена файлов вспомогательных частей не являются публичным контрактом. Электротепловой координатор переиспользует проводимость и тепло; SI связывает извлечённую сеть с драйверами/приёмниками и обработкой сигналов. Eye/timing не получают отдельных физических решателей.

TypeScript отвечает за builders, ресурсы, задания и отчёт. Подготовленные модели, сетки и матрицы остаются в Rust. Пользовательский sweep.evaluate вызывается между расчётами, не для каждой численной операции.

### RoutingBoardV2 как входной формат обмена

По предложению пользователя RoutingBoardV2 служит входным форматом обмена, а не внутренней моделью всех решателей. На входе analyze адаптер проверяет и преобразует его во внутренние данные Rust. Смена формы внешнего контракта локализуется в этом адаптере; solver-модули не читают поля RoutingBoardV2 и native-объекты EasyEDA напрямую.

```text
EasyEDA → экспорт RoutingBoardV2 → адаптер входа analyze
                                    ↓
                       внутренние данные платы
                                    ↓
                  геометрия / контакты / подготовка
                                    ↓
                    сетки и модели нужного анализа
                                    ↓
                              решатель
```

Внешние модели, stackup, материалы и сценарий DSL дополняют постановку расчёта; адаптер платы не придумывает их из отсутствующих данных. Преобразование выполняется до физической подготовки, без предварительного построения всех сеток и моделей всех анализов. Расчёты без платы по-прежнему возможны.

Внутренние данные ориентированы на вычисления: единообразные единицы и системы координат, медь/слои, контакты, индексы и связь с исходными объектами для диагностики и отображения результатов. Это не новый публичный универсальный JSON и не копия всех полей внешнего DTO. Одну обязательную сетку для всех физических методов не вводим. Конкретные внутренние типы уточняются по потребностям модулей; повторно пригодные примитивы не дублируются без причины.

Граница преобразования — один адаптер/модуль, не требование поместить парсинг, проверки и геометрию в одну большую функцию. Он сохраняет необходимые исходные идентификаторы и сообщает о потерях/неподдержанных данных. Кеш не должен скрывать изменение смысла преобразования после обновления адаптера.

**Ограничение заменяемости:** если новый формат иначе записывает уже поддерживаемые сведения, достаточно изменить/добавить адаптер. Если понадобятся новые физические сведения или возможности (например, ранее не поддерживаемая структура перехода), могут потребоваться изменения внутренней модели и решателя. Адаптер не восстанавливает медь, потерянную экспортёром, и не отменяет сравнение с исходной CAD-платой.

## 4. CPU и возможность будущего GPU

**Уточнение пользователя:** используем концепцию PCB board packer — передаём самодостаточную расчётную проблему и получаем результат. TS builder собирает данные проблемы; процессный worker выполняет расчёт через Rust и возвращает результат/диагностику, отдельно передаёт прогресс. Обязательная пользовательская сессия prepare/update/dispose не вводится. Это внутренний протокол исполнения, не новый DSL.

Основа для адаптации: `src/pcb-layout/run-pcb-layout-pool.ts` (workerpool с workerType process, очередь, AbortSignal/cancel, timeout), `run-pcb-layout.worker.ts` (прогресс и сериализация ошибок), native `contract.ts` (problem → solution), `solve-cache.ts` (ограниченный кеш по полному входу). Переиспользуем концепцию и подходящий код, без предварительного общего compute-runtime. Жёсткий лимит native RAM и кооперативная отмена внутри численного ядра не считаются уже реализованными этими средствами; их требуется проверить отдельно. Отмена синхронного native-вызова может требовать завершения worker, а не только сообщения ему.

Долгоживущий worker и внутренний ограниченный кеш допустимы как оптимизация. Результат должен оставаться корректным после очистки кеша или перезапуска worker; пользователь не управляет скрытым порядком подготовки. Ключ полного результата включает все значимые входы и версию численного ядра; внутренние подготовленные части можно переиспользовать по их собственным зависимостям. Дисковый кеш, транспортные handles и подробные политики освобождения не становятся обязательными первой версией. Замыкания sweep.evaluate исполняются в TS и создают очередные проблемы, не передаются в Rust как сериализуемые функции.

Ограниченный бюджет распределяется между независимыми вариантами/частотами, подготовкой и работой внутри большой задачи. Вложенные уровни не умножают потоки без ограничения. Одновременные расчёты ограничиваются также RAM. Бюджет backend учитывает процессы placement и анализа; один `.node` сам по себе не создаёт общего состояния между процессами.

Для будущего GPU приняты границы:

- Физическая постановка отделена от исполнения и размещения памяти.
- Подготовленная система и рабочие буферы могут жить между вызовами.
- Границы исполнения достаточно крупные: решение системы, применение оператора, пакет взаимодействий, FFT; без абстракции на каждом скалярном сложении.
- Внутренние данные не обязаны немедленно материализоваться в JavaScript-массивы. Будущий GPU сможет сохранять рабочие данные между операциями.
- Ускоряются подходящие участки; перенос всей геометрии и каждого анализа не обязателен.

Из packer могут пригодиться подходы к долгоживущему runtime, буферам, очередям, памяти и отказам. Его GPU-ядра размещения не заменяют физические ядра. Универсальный compute-framework и GPU анализатора сейчас не создаются. Добавление GPU не требует нового DSL; автоматическая переносимость всех CPU-алгоритмов не обещается.

GPU placement может оставаться в общем addon при CPU-анализаторе. Анализ не должен требовать или инициализировать GPU лишь из-за наличия его кода в бинарнике.

## 5. Порядок реализации и зависимости

Подробный [план P0–P15](implementation-plan.md) уточняет прежние крупные этапы и является основным документом задач/зависимостей. Весь согласованный состав сохраняется; первый сквозной физический результат — DC по реальной меди.

| Этапы плана | Содержание |
| --- | --- |
| P0–P2 | Уточнение транспорта и источников → экспорт EasyEDA → корпус ≥20 плат → аудит и независимые эталоны |
| P3–P5 | Две библиотеки и общий addon, problem/runtime → физическая геометрия/mesh/refill → DC |
| P6–P8 | Общее электрическое ядро → извлечение линий/via/PDN и сокращение моделей → AC/transient PI |
| P9–P10 | Thermal/радиаторы → электротепловая связь; thermal может развиваться после готовности P4/P5 |
| P11–P13 | SI/impedance/TDR/eye/timing/RF → EMI coupling/conducted → планарный full-wave/антенны/излучение |
| P14–P15 | Полная интеграция исследований/вариантов → регрессия, примеры и поставка |

Кеширование, измерение затрат и минимальный sweep появляются с первых рабочих расчётов, не откладываются на конец. Сокращение/fitting добавляются с подробными моделями. Риск применимости планарного EM проверяется на раннем этапе P2/P3 до полноценного P13. Аудит V2 и корпуса не подменяется чтением нескольких JSON; [проверка достаточности](routing-board-v2-sufficiency.md) содержит конкретные пробелы G1–G7.

## 6. Численная точность: F64 по умолчанию

**Последнее решение пользователя заменяет раннюю проверку F32:** математические расчёты анализатора выполняем в F64 по умолчанию. Сейчас не реализуем и не тестируем отдельный F32-путь. Возможный переход к F32 или смешанной точности оставляем будущей оптимизацией. Действующие F32/FTZ/FMA-правила placement остаются без изменений; решение относится к новому анализатору.

- Для F64 проверяем время до приемлемого результата, пиковую память, сходимость и физические величины: напряжения, токи, потери, температуры. Это проверка решателя, не сравнение двух точностей.
- F64 не объявляется абсолютным эталоном: нужны аналитические/независимые сравнения, проверка балансов и сходимости по сетке и временному шагу. Малая невязка сама по себе не гарантирует малую ошибку результата плохо обусловленной системы.
- В ранний набор включаем обычные и трудные случаи: узкие перемычки, малые падения напряжения, контрасты свойств; при появлении AC/SI — резонансы и слабую связь. Численные допуски задаём по наблюдаемым физическим величинам, а не одним универсальным процентом.
- Локальный F32 допустим только для заведомо подходящей операции с подтверждённой точностью и полезным ускорением. Даже простая формула сопротивления не переводится автоматически в F32. Эти исключения не являются задачей начального этапа; два движка или универсальная иерархия числовых типов не нужны.
- Выбор точности локализуем в численных модулях. DSL и контракт платы не закрепляют F64 как обязательную арифметику будущего GPU. Преобразования форматов и стоимость передачи данных учитываются явно.
- Смешанная точность, например F32-решение с F64-проверкой и уточнением, остаётся будущим вариантом оптимизации, а не обязательной первой реализацией. GPU сейчас не реализуем; его поддержка F64 не становится условием работы анализатора.

Базовый выбор F64 не определяет автоматически порядок редукций, FMA, обработку subnormal и воспроизводимость между платформами. Эти детали проверяются с выбранными библиотеками; правила packer не переносятся на анализатор молча.

## 7. Уточнения внутри плана

Выбор [библиотек Rust](rust-library-candidates.md) согласован на уровне набора и назначения; версии/features и пригодность на целевых сборках проверяются при реализации. Модули, математические основы, CPU/GPU-граница, F64 и передача проблемы по концепции packer определены. Согласованы первоочередной аудит и корпус не менее 20 плат. В плане уточняются:

| Вопрос | Что требуется уточнить в плане |
| --- | --- |
| Достоверность входной меди | Аудит RoutingBoardV2 на реальном экспорте: Pour/Fill, отверстия, аппроксимация, площадки, via, контакты; поведение при недоступной заливке и недостающих правилах refill |
| Подготовка и жизненный цикл | Самодостаточная проблема → результат по концепции packer; внутренние зависимости и пределы кеша, без обязательных пользовательских сессий |
| Исполнение задания | Адаптация процессного пула packer; проверить отмену native-вызова, память, сбой worker и статус частичных результатов |
| Контроль качества расчёта | Набор эталонов по этапам, допуски, критерии сходимости и применимости; различать невалидный вход, недостигнутую точность и отрицательный результат пользовательского check |
| Объём этапов | Проверяемый сквозной результат каждого этапа, ограничения размеров и поддерживаемых моделей; широкий согласованный состав не означает одновременную готовность всех методов |

Эти вопросы распределены по [подробному плану](implementation-plan.md); [состав корпуса](validation-corpus.md) уточняет тестовые случаи. Точные имена crate, детали IPC, версии зависимостей и частные схемы интегрирования можно выбирать внутри соответствующих задач; они не требуют новых пользовательских DSL-методов. Документ не разрешает начать реализацию.
