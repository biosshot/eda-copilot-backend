# Следующее задание: одна N-API оболочка для packer и analyze

Статус: задание для отдельной реализации после приёмки Rust-импорта 2026-10-21. Выполнить только описанную часть. Не начинать следующий этап автоматически.

## Цель

Получить один production Node addon, использующий две обычные Rust-библиотеки: pcb-board-packer и pcb-analyze. Существующий placement продолжает работать через прежний загрузчик; новая функция позволяет вызвать уже реализованный импорт V2 из Node. Это механическое разделение границы N-API, без новой физики.

## До изменения

1. Прочитать корневой AGENTS.md, native/pcb-board-packer/AGENTS.md и применимые инструкции затрагиваемых TS-модулей. Сохранить F32-контракт packer и отдельный F64-контракт analyze.
2. Проверить native/pcb-board-packer/src/lib.rs, build.rs, Cargo.toml/Cargo.lock, index.cjs, platform.cjs, scripts/build-native.mjs, package.json и существующий TS-загрузчик. Поискать остальные места сборки/пакетирования/CI.
3. Снять перечень фактических экспортов текущего addon и результаты version/numeric-contract функций. index.d.ts не считать единственным источником: сверить его с lib.rs и реально загруженным модулем. Выбрать один короткий детерминированный CPU replay packer и сохранить вход/результат до изменения вне исходных fixtures.

## Что сделать

- Создать host crate native/node-addon с cdylib и N-API зависимостями. Обычные Rust-библиотеки подключаются path dependencies; второго production addon нет.
- Превратить pcb-board-packer в обычную библиотеку. Перенести N-API registration и адаптацию ошибок в host. Предоставить минимальный Rust API для существующих операций; не раскрывать все внутренние модули и не переносить solver-алгоритмы.
- Сохранить поведение каждого существующего binding: имена JS-функций, аргументы, результаты, ошибки, версии контрактов, локализацию/восстановление координат, thread-local float guards, обработку сбоев GPU и исходный порядок выполнения. Ошибки host не должны случайно менять InvalidArg/GenericFailure и сообщения.
- Не накладывать F32/FTZ-режим packer на analyze. Вход в analyze не инициализирует GPU; один addon не означает общий численный режим или общий solver runtime.
- Перенаправить native:build на host. Сохранить прежний рабочий путь JS-загрузчика и имя устанавливаемого platform binary, если для цели нет необходимости менять их. Совместимый loader загружает один и тот же файл; отдельную копию addon для analyze не создавать.
- Сохранить действующие target/CRT flags, feature forwarding, vendor patches и версии зависимостей. Учитывать, что Cargo patches/workspace profiles действуют от корня сборки. Не отключать GPU packer глобально ради CPU-only analyze и не обновлять библиотеки попутно.
- Добавить одну внутреннюю функцию addon: importAnalysisBoard(json: string), возвращающую объект { imported: boolean, accepted, diagnostics } из существующего import_json. Невалидная JSON-строка возвращает диагностический отчёт, а не успешный пустой результат. Внутреннюю модель Board наружу не сериализовать; новое публичное семейство API пакета не создавать.
- Добавить корректную TS-декларацию нового binding и синхронизировать затронутые декларации существующих экспортов. Не менять публичный Analysis DSL.
- Обновить документацию сборки/границ и CHANGELOG. Сборочные артефакты и временные baseline-результаты в Git не добавлять.

## Границы: чего не делать

- Не создавать worker, очередь, timeout/cancel API, прогресс, кеш или compute-runtime. Это следующая отдельная задача.
- Не реализовывать геометрию контактов, boolean операции, mesh, DC/thermal/SI/PI/EMI, refill или аналитику площадей.
- Не менять V2, экспортёр EasyEDA, сохранённые платы, численную политику, scoring, параметры поиска, GPU kernels и качество placement.
- Не добавлять публичные prepare/dispose sessions, handles, новые CLI или второй launcher.
- Не упрощать строгий импорт для прохождения тестов и не скрывать diagnostics. Полноценная физическая готовность по imported: true не заявляется.

## Условия приёмки

1. Сборка из исходников даёт один устанавливаемый platform .node. Прежний загрузчик работает; список старых runtime exports и version/numeric-contract результатов сохранён. Новая функция добавлена к тому же модулю.
2. Через binding импортируются все восемь fixtures. accepted и diagnostics совпадают с Rust API, включая пути/source IDs и различие error/missing/limitation. Есть отрицательные тесты: malformed JSON, неизвестный слой, неизвестное поле; есть успешный случай без stackup и с unavailable fill.
3. Интеграционные тесты не пропускаются молча из-за отсутствующего addon. Если сборка отсутствует, тест новой функции явно завершается ошибкой с объяснением.
4. Пакетирование проверяет наличие и загрузку нужного бинарника, включая установленный/упакованный пакет. Требуются исходная сборка и работа из пакета, а не только require локального старого .node.
5. Короткий CPU replay packer после переноса совпадает с baseline по детерминированным результатам; служебное время сравнивается отдельно. Прежние native/focused TS/recovery проверки проходят. Смешанный порядок вызовов packer → analyze → packer не меняет результаты или численные режимы. Проверяется сохранение независимости от доступности GPU для импорта.
6. Rust tests analyze и packer, сборка native:build, typecheck и build проходят. Выполнить проверки согласно AGENTS.md; учитывать изменившийся manifest host. GPU/platform проверки, недоступные на текущем хосте, явно перечислить, не выдавать за пройденные. Полную дорогую серию placement benchmarks без новой причины не запускать.
7. Diff ограничен библиотечной/API-границей, сборкой, декларациями, нужными тестами и документацией. Нет попутных оптимизаций или изменения сохранённых входов.

## Что вернуть на проверку

Перечень изменённых файлов и перемещённых bindings; схема трёх crates; команды с результатами и ограничениями платформы; сравнение старого/нового списка экспортов и CPU replay; результаты Node-импорта восьми плат и package smoke test. Не коммитить и не переходить к worker до отдельной приёмки валидатором.
