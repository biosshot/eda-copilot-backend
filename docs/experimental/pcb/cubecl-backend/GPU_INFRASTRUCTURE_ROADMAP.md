# Общая GPU-инфраструктура CubeCL

Дата: 2026-09-30. **Статус: завершено на Windows x86-64 / RTX 3060 Laptop.** Реализация, приёмка и ограничения записаны в [отчёте](GPU_INFRASTRUCTURE_RESULTS.md). Другие OS/GPU этой проверкой не охвачены.

Предыдущая задача переноса block solver завершена в commit `8ff7564`: [roadmap](ROADMAP.md), [результаты и ограничения](RESULTS.md). Этот план выделяет её работающую инфраструктуру для следующих потребителей, сохраняя алгоритмы, качество и производительность block solver. Подробные roadmaps board packer и post-place/refiner будут отдельными документами после этого этапа.

## Цель и границы

- Один общий GPU-модуль **внутри существующего Rust crate и того же `.node`**. Не отдельная библиотека поставки, процесс или сервис.
- Rust/CubeCL, текущий Vulkan/wgpu backend; один лениво созданный runtime/device/client на процесс, общий для native threads. Между процессами сохраняется OS lease.
- Сначала CPU F64 и GPU F64. Будущий переход **всех** floating вычислений, включая CPU generator и solver, на F32 — отдельная задача без срока. В этом roadmap точность не меняется.
- Сохраняются массовые GPU batches, распределение кандидатов/workgroups по GPU lanes, resident данные, переиспользование буферов и возврат shortlist. Общая оболочка не должна превращать это в последовательные вызовы на каждого кандидата или CPU пересчёт всех оценок.
- Поставка — один платформенный `.node`, желательно не более 20 МБ; без helper/compiler DLL, OpenCL runtime и LLVM/CPU JIT. Системные GPU драйверы остаются внешними.
- Сейчас не переносим board scoring, post-place/refiner, islands или TypeScript-логику; не меняем поиск, веса, pruning, ранжирование, thresholds и публичные NAPI/TS контракты.

Выделение инфраструктуры само по себе не обещает нового ускорения. Результат — следующий scorer может использовать готовый runtime без копирования кода из block solver.

## Что выносим и что оставляем

| Область | Общая инфраструктура | Доменный модуль |
|---|---|---|
| Устройство | Выбор адаптера, client, capabilities, lazy init, состояние доступности | Требуемые возможности конкретного scorer и проверка поддерживаемого входа |
| Доступ | Mutex, OS lease, одна GPU-сессия, обработка runtime panic/failure | Выбор CPU/GPU, порог окупаемости, управление поиском |
| Память | Выделение и повторное использование scratch buffers, безопасная область их использования | Формат compact poses, содержимое и размеры buffers, resident templates/frames и ключи кешей |
| Вычисления | Минимальные численные GPU helpers и compatibility probes, уже нужные runtime | Score terms, kernels, geometry caches, pruning, rank/tie-break, shortlist |
| Восстановление | Причина недоступности/сбоя и корректное завершение сессии | Сохранение исходного входа, отбрасывание частичного результата, повтор своего этапа на CPU |
| Диагностика | Device, initialization count, mutex wait, scratch bytes, причина отказа | Batches/candidates, времена стадий, checkpoints, качество и итоговый результат |

Предлагаемая структура, имена уточняются при реализации без изменения границ:

```text
native/pcb-board-packer/src/
  compute/
    mod.rs         # внутренний API; feature gates
    gpu.rs         # runtime, session/lease, capabilities, ошибки и статистика
    workspace.rs   # scratch buffers, если выделение в файл упрощает код
    numerics.rs    # точное GPU округление и arithmetic probe
  block_solver/
    cubecl.rs      # Engine, guard, resident buffers и запуск batch kernels
    gpu_kernels.rs # block scoring/pruning/ranking
    gpu_frontier.rs
```

Направление зависимостей: `block_solver → compute → CubeCL/wgpu`. Общий модуль не импортирует `block_solver`. Board packer и post-place подключатся к нему позже. Не вводить универсальный solver, набор абстрактных backend traits или общий scorer на основании одного потребителя. MST, collisions и прочие общие по названию операции выделять только после сопоставления их реальных формул и представлений в следующей доменной задаче.

## Контракты выделения

1. **Жизненный цикл.** Сохранить текущую lazy initialization и поведение состояний `New/Ready/Busy/Disabled`. Занятый другим процессом GPU означает CPU fallback; текущий интервал повторной проверки доступности не менять. После runtime failure не создавать новый context и не повторять GPU попытку внутри того же доменного вызова. CPU-only сборка не должна требовать GPU dependencies.
2. **Capabilities и ошибки.** Отделить сведения об устройстве от требований scorer. Нынешний путь требует F64 и U64 для точного округления; требования и выбор адаптера сохраняются. Неподдерживаемый/численно небезопасный доменный вход проверяется до GPU работы и не отключает общий runtime для других заданий. Различать занятость lease, отсутствие совместимого устройства, запрет GPU, arithmetic incompatibility и runtime failure; причина должна быть доступна вызывающему модулю без разбора текста сообщения.
3. **Workspace.** Сохранить один общий workspace и последовательный доступ к нему: это уже измеренный вариант. Убрать зависимость общего API от значений вроде «slot 16 означает block frontier»: использовать локальные домену обозначения/области scratch. Не создавать отдельные contexts или большой пул заранее. Уточнить владение handles: данные scratch действительны только в защищённой операции; их нельзя использовать после передачи этих буферов следующему заданию. Проверить чередование разных размеров и потребителей тестовой нагрузкой.
4. **Граница блокировки.** GPU операция включает связанные upload, dispatch и необходимый readback до безопасного повторного использования scratch. Генерация CPU кандидатов остаётся вне этой блокировки. Не добавлять лишних синхронизаций/копирований между kernels существующего батча.
5. **Resident данные.** `Engine` и его статические buffers/caches остаются доменными и относятся к тому же runtime/client. Общая инфраструктура не угадывает ключи кешей или моменты изменения геометрии. После отказа runtime домен отбрасывает свой Engine; handles нельзя повторно использовать в другом runtime. Механизм автоматического восстановления устройства и эпох кешей сейчас не нужен.
6. **Численная совместимость.** Сейчас `gpu_runtime.rs` вызывает `block_solver::gpu_kernels::rounding_probe`. Перенести probe и необходимые ему `rp/grid_quotient` helpers в общий слой, сохранив операции и граничные проверки. CPU `geometry::round_placement` остаётся неизменённым эталоном. Общая GPU арифметика не должна тянуть за собой block scoring. Не заменять точное округление обычным делением, не менять FMA/fast-math политику.
7. **CPU replay.** Runtime возвращает ошибку, а не вызывает solver. Block controller повторяет **весь исходный текущий native block call**, без частичных GPU poses/checkpoints; отдельный deferred-pairs call повторяется с его исходным `pairSeed`. Для будущих board/refiner границу восстановления определят их собственные roadmaps — нельзя автоматически наследовать «пересобрать блок».
8. **Совместимость управления.** Сохранить действующие `PCB_BLOCK_*` flags, fault injection, profiling и benchmark interfaces. Если понадобятся общие имена, явно описать их приоритет и совместимость; не менять молча смысл старых переменных. `ready()` остаётся проверкой состояния без принудительной инициализации.
9. **Освобождение ресурсов.** При сбое освобождаются принадлежащие сессии scratch buffers и OS lease; проверить передачу lease другому процессу. Не обещать полное освобождение всей VRAM/context до выхода процесса: глобальный CubeCL client/allocator может удерживать ресурсы. `workspaceBytes` — размер scratch, а не всей GPU памяти.

## Для чего готовим инфраструктуру дальше

Продолжение оформлено отдельными планами: **[Board Packager](BOARD_PACKAGER_GPU_ROADMAP.md)**, затем **[Post-place / Refiner](POST_PLACE_GPU_ROADMAP.md)**. Оба пока не реализованы; описание ниже сохраняет исходные ориентиры инфраструктурной задачи.

**Следующий предполагаемый roadmap — Board Packager.** Кандидат на массовый GPU score — `solver.rs::score_positions` и его использование в поиске, local improve и repair. Нужны собственные batches compound primitives, границы платы/области, hard constraints, relations и сохранение rank semantics. Контроллер поиска остаётся CPU; существующую маршрутную проверку shortlist сначала сохраняем. Точные kernels, границы восстановления, thresholds и этапы переноса определим после отдельного чтения/профилирования. В историческом Telemetry профиле два board вызова занимали около 84.4 с; PortableScope также указывает на дорогой board search, но его тот capture не является валидным placement reference.

**Затем отдельный roadmap — Post-place / Refiner.** Изучить общий `post_place.rs::score` и массовые оценки из `post_place_refine.rs`. Локальная доводка блоков и финальная доводка платы уже используют общий native refiner: не создавать две GPU реализации. CPU orchestration, принятие улучшений и зависимости Micro-A* не переносить автоматически. Потребуются собственные измерения score/geometry/route и полного refinement: сокращение score time не равно такому же ускорению всего этапа. При фиксированном timeout быстрый backend может проверить больше кандидатов; сравнение одинаковой работы и качества за тот же бюджет времени нужно разделять.

**Пока вне очереди:** TypeScript orchestration, alignment/portfolio как отдельные GPU алгоритмы, passive island и остальные island solvers. Наличие score или циклов само по себе не оправдывает перенос. Alignment/portfolio не всегда однопроходные, но сначала выгоднее переиспользовать будущий общий scorer в их существующих вызовах. В историческом Telemetry профиле все 13 passive-island вызовов заняли суммарно около 7.5 мс — основания ставить этот solver впереди board/refiner нет. Источник исторических данных: [Telemetry current profile](../placement-performance-2026-09-28/Telemetry/current-profile/README.md); перед следующим roadmap обновить профиль, не считать прежнее распределение времени неизменным после ускорения block solver.

Эти направления объясняют требования к инфраструктуре и предполагаемую последовательность. Они не являются подробными планами или разрешением включить дополнительные GPU solver в текущую миграцию.
