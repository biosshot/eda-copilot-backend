## Границы задачи и обязательные правила

1. Только native block solver и его CPU/GPU backend, **включая внутриблоковую доводку singles и штатные pairs**. Контрольный тяжёлый вход — сохранённый FPGA из PortableScope; по последнему поручению пользователя проверять также несколько других блоков, по отдельности и вместе, с полным циклом сборки. Board packing, общий post-placement refinement и вся плата исключены из текущей реализации. Завершение одного Beam не означает завершение оптимизации блока.
2. Единственный GPU backend новой реализации — **CubeCL на Rust**. Последнее решение пользователя 2026-09-30: **на первом этапе допустим GPU F64**, CPU backend и CPU generator пока сохраняют F64. **В будущем на F32 переходят абсолютно все floating вычисления, включая CPU generator и CPU solver; срок не определён, это отдельная будущая задача.** Ранее согласованный GPU F32 остаётся разрешённым, но больше не является обязательным первым этапом. Граница первого этапа: CPU F64 → GPU F64 → readback F64. Граница ранее согласованного промежуточного F32 пути: CPU F64 → GPU F32 → readback F32 → расширение в CPU F64; расширение не восстанавливает потерянную точность. В текущем переносе CPU reference не менять; для будущей миграции сохранить воспроизводимый F64 reference. ID, индексы, ordinals и hard count сохраняются целочисленными. Старые OpenCL файлы — источник алгоритмов и исторический performance reference; OpenCL runtime, OpenCL C kernels, C/C++ helper и его DLL в новый backend не включать.
3. CPU остаётся полноценным F64 backend. Нет совместимого GPU/драйвера или возможностей выбранного режима точности/runtime, ошибка инициализации/исполнения, неподдерживаемый или численно небезопасный вход — **перезапуск всего текущего блока на CPU с исходного входа**, без продолжения из частичного GPU состояния. Для первого GPU F64 этапа отсутствие F64 является причиной CPU fallback; после реализации и проверки F32 пути отсутствие F64 не мешает этому пути. Маленькие задачи направляются на CPU до подготовки GPU буферов. Подробный контракт перезапуска описан ниже.
4. На GPU переносится **вся массовая оценка кандидатов Beam и singles, а также применимых штатных pairs**, включая дешёвую нижнюю границу, активные члены полного score, hard count, отсечение и shortlist. Не оставлять CPU проход по всем кандидатам для вычисления части score, hard count или опорных полных оценок. Около 90 с CPU singles — исходная стоимость стадии, которую тоже требуется ускорить за счёт массовых GPU оценок; не считать её неизменным CPU остатком будущего решения.
5. CPU генерирует компактные poses, управляет Beam и восстанавливает полную геометрию выбранных кандидатов. Ориентации, площадки, правила, фиксированное состояние и кеши остаются на GPU; буферы переиспользуются. Обрабатывать независимых кандидатов массово, без dispatch/readback на каждого кандидата или каждый term. Последовательные зависимости Beam не объединять ценой изменения алгоритма.
6. CPU работа на малом маршрутном shortlist допускается в уже проверенной гибридной схеме: она давала 8.318 с. Это не разрешение оставить массовый base score на CPU. Новые границы CPU/GPU согласовывать, если они меняют эту архитектуру.
7. Переиспользовать существующую быструю организацию OpenCL: compact poses, resident frames, fixed MST/pad caches, GPU pruning и bounded ranking. Перевод OpenCL C в Rust/CubeCL требует адаптации языка; заново придумывать генератор, Beam, формулы или алгоритм отбора не требуется.
8. Минимум дублирования: общий Rust код вычислительных правил там, где CubeCL позволяет, сначала с F64 на CPU/GPU и с возможностью последующего F32 переноса; разные типы и оболочки исполнения допустимы. Не копировать весь scorer только ради разных floating types и не достигать общности ценой потери уже измеренной скорости. Архитектурное противоречие выносить пользователю.
9. Все изменения структур, вычислений, кешей и порядка отбора проверять на результатах. Hard constraints, inventory, locked poses, допустимые ориентации и checkpoint политики сохраняются. Для неизменённого CPU F64 backend сохраняется точный CPU reference. Для GPU F32 точное совпадение score/poses с CPU больше не обязательное условие: пользователь принял потерю точности и показанное близкое по качеству FPGA решение. Изменения выбранных поз и ориентаций из-за F32 измерять и показывать вместе с качеством; разрешение не распространяется на нарушение ограничений или любое произвольное ухудшение. Новую общую численную границу допустимого ухудшения самостоятельно не назначать.
10. Подробные CPU/GPU сравнения выполняются **в отдельных валидационных тестах**, вне таймера. В обычном GPU режиме не пересчитывать его кандидатов на CPU ради проверки. Проверка валидности GPU ответа и fallback при ошибке не являются двойной оценкой каждого кандидата.
11. Итоговая поставка — один `.node` для каждой поддерживаемой OS/arch, ориентир **до 20 МБ**, без отдельно поставляемого helper/compiler DLL; системные библиотеки и GPU драйверы внешние. CPU исполняет обычный нативный Rust; **не включать LLVM/CPU JIT backend**. Декларация `#[cube]` должна по возможности сохранять обычное Rust исполнение общей функции. OpenCL helper остаётся только в архиве прежнего эксперимента.
12. Новое решение об алгоритме, backend архитектуре, допустимом дрейфе или компромиссе скорости/качества за пределами записанных разрешений: записать конкретные варианты и данные, остановить зависимую работу и спросить пользователя. Согласованные первый GPU F64 этап, последующий GPU F32 перенос, массовые оценки singles и перезапуск блока на CPU повторного разрешения не требуют. Предложения ниже не выдавать за уже принятые пользователем новые компромиссы.
13. Один лениво созданный GPU runtime/device/client **на процесс**, общий для native threads и последующих блоков. Отдельный thread или блок не создаёт собственный GPU backend. Операционные буферы разных заданий изолированы: один workspace либо небольшой пул workspace на общем runtime. Размер пула выбирать по измерению 1/2/4 native workers: общее wall time, GPU throughput, mutex/lease wait, peak buffers, количество инициализаций и отсутствие смешивания результатов. Несколько Node process имеют отдельное адресное пространство; конкуренцию за физическую GPU измерять и ограничивать отдельно. Пользователь разрешил исследовать небольшой пул, но не дал оснований создавать несколько GPU contexts на каждый поток.

## Этапы точности и численная устойчивость

Последнее решение 2026-09-30 разрешает сначала восстановить быстрый массовый путь на **GPU F64**, включая оценки singles, а затем переходить на F32. Это отменяет требование сразу реализовывать только GPU F32. Перенос архитектуры и снижение точности проверяются отдельно; F64 сам по себе не гарантирует одинаковый порядок редукций и результат CPU/GPU. Сравнивать реальные kernels, shortlist и checkpoints; разрешение на F32 drift не считать автоматическим оправданием ошибки F64 переноса.

Рабочая гипотеза пользователя: на F64 ускорение будет примерно **в 1,6 раза меньше**. Для планирования это трактуется как меньшее ускорение относительно будущего F32 варианта при одном CPU baseline (`S_F64 ≈ S_F32 / 1.6`), **не измеренное ускорение и не утверждение «F64 ускоряет CPU в 1,6 раза»**. Коэффициент не назначает новый порог приёмки и не применяется автоматически к историческим 8.318 с: архивный OpenCL уже работал в F64. Измерять Beam, singles и полный блок отдельно; нынешние 90.5286 с singles не фиксировать как неизбежный остаток. Пользователь уточнил: будущий F32 перенос охватывает абсолютно всё, включая CPU, но неизвестно когда; он не блокирует завершение нынешнего F64 переноса.

Следующие правила сохраняют ранее согласованный промежуточный CPU F64 / GPU F32 вариант и численные требования будущей миграции. Будущий полностью F32 путь потребует отдельной проверки generator, CPU scoring и fallback в новой точности; нижеописанное расширение GPU readback в F64 не задаёт его окончательный контракт. Проверки ограничений, finite/range, pruning и корректности восстановления нужны и для первого F64 этапа.

Предыдущее решение пользователя 2026-09-30 после просмотра [F64/F32 проверки](../block-precision-f32-2026-09-30/README.md): результаты по сути похожи, потеря точности допустима ради GPU F32. Показанный пример (+0.031533% final score после восстановления исходной F64 геометрии, изменения 16/19 poses и 6 ориентаций) принят как основание этого решения; это **не автоматически универсальный порог 0.031533%** для остальных входов. Исследование было CPU search с F32 generator, поэтому будущий F32 этап ещё должен проверить выбранную тогда границу CPU/GPU и реальные CubeCL kernels.

- CPU создаёт compact poses и исходное состояние в F64. На границе загрузки floating данные преобразуются в F32; GPU хранит и считает их в F32. Возвращаются только shortlist/winners и их необходимые floating результаты в F32. Host расширяет эти значения в F64 для существующего Rust/TS контракта; размеры и типы GPU буферов от этого не становятся F64. CPU восстанавливает полную геометрию по исходным poses/ID, сохраняя locked state и метаданные; возвращённый GPU score не объявлять заново вычисленным F64 score.
- Проверять finite/range при конвертации, исполнении и readback, включая промежуточные суммы, произведения и score. Ожидание, что обычные scores помещаются в F32, не заменяет проверку `NaN`/`Inf` и переполнений. Ошибка или численно неподдерживаемый вход вызывает диагностируемый CPU fallback, без saturation/clamping score ради продолжения.
- Для уменьшения ошибки применять проверяемые приёмы в F32: перенос геометрии в локальную систему координат до сужения из F64, вычисление разностей близких величин в таком frame, устойчивый порядок редукций, попарное либо компенсированное суммирование длинных сумм. Масштабирование допустимо только при сохранении физических единиц и исходных весов/формул после обратного преобразования. Выбор приёмов принимать по сравнению результата и стоимости, не добавлять их формально во все kernels. Первый GPU F64 этап разрешён явно; в отчёте о будущем F32 пути не скрывать вычисления F64 или массовый CPU пересчёт под названием F32.
- Отдельный обязательный тест — геометрические границы. Найденный случай C27/C32: depth около `9.54e-7` мм в F32 включал штраф 10 миллионов для F64 reference. Различать численную неопределённость predicate и реальное нарушение clearance. Не менять физический clearance и не вводить произвольный глобальный epsilon, который разрешает реальные нарушения. Оценку ошибки выводить из representation, масштаба и операций; неоднозначные hard-boundary входы, для которых нет проверенной безопасной обработки, направлять в CPU fallback. Штатное округление выходных poses до 0.001 мм не является разрешением округлять всю геометрию или уменьшать зазоры в kernels.
- Safe pruning должно учитывать F32 погрешность нижней границы и накопления score; кандидата в пределах численной неопределённости не отбрасывать преждевременно. Сохранять ordinals и детерминированные tie-break правила. Проверять near ties, границы shortlist/diversity, hard count, cache reuse и окончательный выбор. Не менять Beam width, candidate generator, набор terms или objective ради маскировки численной разницы.
- Offline validation сравнивает F64 reference, GPU F32 результат после расширения и выбранную расстановку, восстановленную на исходной F64 геометрии. Отдельно сохранять raw F32 score, его F64 расширение, F64 переоценку качества, нарушения и расхождения poses/checkpoints. F64 проверки остаются вне production candidate scoring и таймера. Значительное новое ухудшение или необходимость ослабить hard constraint — новый компромисс для обсуждения, а не уже принятое следствие F32.
- Ранее обсуждавшееся преимущество F32 над F64 в 32–64 раза не было измерением solver. Новая рабочая гипотеза о разнице ускорения в 1,6 раза тоже требует проверки. Реальное время зависит от генератора, Beam/singles, dispatch, transfer, pruning и route shortlist; исторический ориентир FPGA Beam около 8–10 с сохраняется для сравнения, время полного блока устанавливается отдельным замером.

## Восстановление после ошибки: согласованный перезапуск блока

- Единица восстановления — один блок (одна гипотеза/native problem), а не вся плата и не только последний GPU батч. Сохранить исходный неизменённый вход, параметры поиска и исходный seed, если он был частью вызова. Отбросить полученные в неудачной попытке GPU candidates, Beam state, singles/pairs state и checkpoints; заново исполнить весь этот вызов CPU F64 с GPU отключённым. Соседние независимые блоки не перезапускать.
- Для обычного полного вызова CPU заново проходит Beam → singles → разрешённые pairs. Для явного pairs-only continuation воспроизводится исходный контракт этого вызова с исходным pair seed; GPU-промежуточный seed не становится входом fallback. Полный блок, разбитый вызывающим кодом на несколько вызовов, требует хранения исходного входа на соответствующей границе контроллера.
- Не зацикливать retries: одна CPU попытка после GPU отказа; ошибка CPU возвращается штатным способом. Не смешивать GPU checkpoints с результатом CPU перезапуска. Результат CPU перезапуска сравнить с самостоятельным CPU запуском того же входа.
- В диагностике отдельно записывать запрошенные/фактические backend и точность, причину и стадию GPU отказа, потраченное до отказа время, CPU restart time и полное wall time. Fallback не засчитывать как GPU benchmark; пользовательское время включает неудачную попытку.
- Recovery должен работать в release `.node`, в том числе при перехватываемой panic runtime. Исходный `panic = "abort"` не позволяет восстановление через `catch_unwind`; для нового runtime выбран `panic = "unwind"`, до подключения GPU scoring проверить локализацию ошибок и release fault injection. Перезапуск в том же процессе не обещает восстановить принудительное завершение процесса или зависший драйвер; такие случаи отдельно покрываются существующей process isolation/timeout границей, если она задействована.

## Предлагаемые варианты для остальных вопросов

Это рекомендации для обсуждения и проверки, а не отметки выполненной реализации или новые согласованные допуски качества.

1. **Численные границы.** Рекомендация: сначала F64 kernels на сохранённых FPGA candidates и отдельные случаи касания/clearance; перед F32 повторить их с локальными координатами и оценкой ошибки predicate. Считать неопределённые случаи и долю полных CPU перезапусков. При неопределённости сохранять согласованный fallback всего блока. Альтернатива для будущего — точная CPU проверка только неоднозначного малого набора; она меняет границу вычислений и сейчас не принята. `hardCount = 0` проверять вместе с primitive overlap penalties и геометрией: это разные представления ограничений.
2. **Отсечение и отбор.** Рекомендация: отдельный offline режим без pruning на фиксированном наборе candidates; сравнить его с pruning в одной и той же GPU точности. Проверить winners, shortlist membership/order, diversity buckets и ordinals для Beam и singles; повторить для F64 и затем F32. Так ошибка pruning отделяется от F32/F64 drift. Дополнительно сравнить с CPU reference, не подменяя одно сравнение другим. Полные таблицы оценок допустимы только в диагностике.
3. **Качество.** Рекомендация: для сохранённого FPGA фиксировать F64 переоценку восстановленной геометрии каждого checkpoint, hard/overlap нарушения, inventory, locked state, ориентации, площадь, HPWL и картинку. HPWL не объявлять длиной реальных трасс. Сначала добиваться воспроизведения reference для F64 переноса; отличия исследовать и показывать. Для F32 сохранять согласованную приёмку фактического результата без самостоятельно назначенного процента ухудшения. Альтернатива — позже согласовать численные допуски по набору входов. Непокрытые типы входов оставлять под capability guards с CPU fallback; один FPGA не доказывает общую поддержку.
4. **Несколько процессов.** Рекомендация для первого варианта: один активный GPU процесс на устройство через освобождаемую ОС межпроцессную lease; внутри него один runtime и сначала один workspace. Другие процессы при недоступной lease выполняют блок на CPU до GPU подготовки. Проверить освобождение после завершения/ошибки процесса. Альтернативы: ограниченная очередь ожидания либо несколько GPU процессов с общим бюджетом памяти. Выбирать по замерам native workers 1/2/4 и отдельно процессов 1/2/4: throughput, latency, CPU load, peak VRAM, количество инициализаций, ожидание/CPU fallback и отсутствие смешивания результатов. Это можно проверить на сохранённом блоке без запуска всей платы.
5. **Ранняя проверка поставки.** Рекомендация: до полного scorer собрать минимальный release CubeCL F64 kernel внутри одного `.node`, проверить GPU readback, отсутствие helper/compiler DLL, запуск без GPU, размер и обработку отказа.
