# F64 / F32: полный FPGA block search

2026-09-30 пользователь разрешил изолированное исследование точности перед решением о F32 на GPU. Production solver, addon, CPU reference и fixtures не изменены. Исследование не разрешает автоматически менять точность, численные допуски или правила отбора новой реализации CubeCL.

Результат: на этом входе F32 даёт близкое практическое качество после штатного округления выходных координат, но другой путь поиска и другую расстановку. Простая замена F64 на F32 не сохраняет нынешние score predicates. Production-переход не принят.

Последующее решение 2026-09-30: после просмотра этих результатов пользователь принял близкое качество и согласовал **CPU F64 / GPU F32**, включая F32 readback с расширением в F64 на host. Исторический verdict выше описывает момент самого исследования. Текущая принятая спецификация и требования численной устойчивости находятся в [CubeCL roadmap](../cubecl-backend/ROADMAP.md); GPU реализация ещё не выполнена, произвольные новые ухудшения и ослабление физических ограничений не разрешены.

## Метод

- Основной checkout, `feat/block-solver-cubecl`; исходный Rust solver копируется только в игнорируемый `debugging/block-precision-2026-09-30/`. Worktree не создаётся.
- Точный saved FPGA input PortableScope, 19 примитивов (U3 + 18 capacitors). SHA-256 `problem.json`: `9db75277e877b4765cf9ae32b16a698a16b8155101c8a06cc35a80f6a77a640f`.
- Две standalone CPU release сборки из одинаковых исходников. В F32 копии преобразованы floating types, literal suffixes, constants и arithmetic всего исполняемого block solver и его зависимостей, включая генератор и маршрутную оценку. Casts bit keys расширяют F32 bits в `u64`, не меняя floating arithmetic. Формулы, epsilons, Beam width, flags, количество стадий и параметры поиска не меняются.
- Это настоящая F32-арифметика; округление только финального score не используется. Логи сохраняют удержанные Beam states на каждом уровне и геометрию каждого checkpoint.
- F64 результат полностью, включая сериализованные checkpoints, совпал с captured CPU reference (`assert.deepEqual`).
- Исходный F64 scorer отдельно оценивает raw geometry обоих результатов. Он точно воспроизводит F64 scores всех checkpoints.
- Второй отдельный контроль восстанавливает выходные F32 poses с **штатным округлением до 0.001 мм** на исходной F64 геометрии. Это не изменение поискового шага `grid` и не новый геометрический tolerance. Тот же способ восстановления точно воспроизводит F64 reference; сохранение округлённых F32 poses проверено assertion.
- Обратный контроль оценивает сохранённую F64 final geometry через F32 scorer без повторного поиска.
- Это проверка одного полного **блока на CPU**, не всей платы, не GPU/CubeCL и не performance benchmark. Будущий GPU путь сохраняет CPU generator; здесь F32 generator тоже участвовал. Порог CPU/GPU, runtime и production архитектура не менялись.

## Качество после восстановления poses в F64

Score меньше — лучше. Все значения ниже рассчитаны в F64 на исходной геометрии.

| Метрика | F64 search | F32 search |
|---|---:|---:|
| Beam score | 5969.483094641118 | 5943.628256573449 |
| Final score (singles / pairs checkpoint) | 5528.140155316541 | 5529.883368821761 |
| Final hard count | 0 | 0 |
| Площадь envelope, мм² | 480.01784079500015 | 480.1765998950001 |
| HPWL, мм | 87.94000000000001 | 87.519 |

Beam score F32 лучше на 0.433117%; после singles final score хуже на **0.031533%**. Площадь увеличилась примерно на 0.033074%, HPWL уменьшился примерно на 0.478736%. HPWL — геометрическая метрика, не длина реально проложенных трасс.

Первое различие удержанных поз и порядка Beam — глубина 3. Финально изменились 16 из 19 компонентов при сравнении координат с точностью 0.001 мм; изменились 6 ориентаций. Максимальный перенос компонента — 8.543025 мм. Некоторые изменения включают общий сдвиг координат; это не только ошибка хранения последнего разряда. Inventory сохранён, пропусков, дополнительных компонентов и дублей нет, слои не изменились. Вход не содержит locked primitives, поэтому locked coverage этим запуском не установлена. Пары для 19 примитивов штатно не выполняются; пары/checkpoint policy не изменялась.

## Разрыв score на границе зазора

Raw F32 geometry, расширенная обратно в F64 без восстановления на исходной геометрии, даёт final score `20005529.90239374`. Две пары C20/C30 и C30/C21 имеют depth `9.536743128535363e-8` мм. В `overlap_penalty` условие `overlap > 0` добавляет **10 000 000** за каждую пару. Сам hard count остаётся 0: component hard geometry и primitive collision boxes score — разные представления. После штатного восстановления выходных poses эти штрафы исчезают; final F64 score `5529.883368821761`.

Контроль одинаковой расстановки ещё важнее: F64 final geometry получает score `5528.140155316541` в F64 и **`10005528` в F32**. В F32 для C27/C32 появляется depth `9.5367431640625e-7` мм и штраф 10 миллионов. Поэтому различие обусловлено не только F32 candidate generation. Сама оценка геометрической границы чувствительна к преобразованию представления и арифметике.

Эти миллионы не следует интерпретировать как соответствующее физическое ухудшение расстановки. Они показывают разрыв численного predicate, способный изменить ranking/pruning. Подменять его более широким epsilon без решения пользователя в этом исследовании нельзя.

## Проверки и воспроизведение

Из корня backend:

```powershell
node scripts/experiment-block-precision.mjs
node --import tsx scripts/report-block-precision.mjs
```

Для повторной offline-переоценки сохранённых поисков, без повторного search:

```powershell
node scripts/experiment-block-precision.mjs --evaluate-only
node --import tsx scripts/report-block-precision.mjs
```

Проверки выполнены: обе release сборки, полные F64/F32 поиски, точное совпадение F64 reference, оба способа F64 offline evaluation всех checkpoints, контроль одной F64 расстановки через F32, assertions о сохранении intended poses, `node --check` обоих scripts, `git diff --check`. Штатные Rust/TS suites повторно не запускались: production Rust/TS не менялись.

Артефакты в `debugging/block-precision-2026-09-30/`: `manifest.json` с source/input hashes; `runs.json` с hashes использованных search executables; `evaluation-manifest.json` с hashes последующих offline evaluator executables; обе полные solutions, checkpoint geometry, search logs, cross evaluations, `comparison.json`, SVG и `comparison.png`. `wallMs` сохранён для диагностики одного инструментированного вызова, не как сравнение производительности GPU. Последующие evaluator сборки содержат дополнительные диагностические функции; их hashes записаны отдельно от search сборок.

Основные измерения и hashes сохранены также в [results.json](results.json). Картинка: `debugging/block-precision-2026-09-30/comparison.png`, одинаковый масштаб и исходные footprints.

Следующий возможный эксперимент — сохранить F64 CPU generator и проверить F32 массовую оценку с явно согласованной политикой геометрических границ, затем проверить реальные CubeCL kernels и несколько входов. Один этот запуск не устанавливает допустимый drift и не подтверждает F32 для всех плат/GPU.
