## E1 — P1: неверная сторона периодического фронта

Места: `native/analyze/src/electrical/waveform.rs:177,197` (sample), `:263,284` (next), `solve.rs:363–371` (правое состояние события).

`next()` строит границу как `delay + j * period`, а `sample()` заново определяет фазу через `%`. В F64 эти операции не обязаны согласовываться на границе. Например, при period=0.1 граница пятого периода округляется в 0.5, а `0.5 % 0.1` оказывается около 0.1, а не 0. Поэтому источник с нулевым фронтом возвращает последнее значение предыдущего периода вместо первого значения нового.

Это затрагивает и pulse, и повторяемый PWL с разрывом между концом и началом периода. Интегратор вызывает `rhs(Some(event))` для правого состояния, но получает левое значение. Ошибка попадёт в отсчёт точно на событии и может размазываться интерполяцией следующего шага. На чисто резистивной сети проверка энергии этого не обнаружит: диссипация и работа источника всё равно равны для ошибочно выбранного значения.

Минимальная постановка для production-регрессии:

```js
const a = analysis();
const circuit = a.circuit({
  nodes: ["gnd", "p"], reference: "gnd",
  ports: [{ id: "p", positive: "p", negative: "gnd" }],
  elements: [
    { id: "R", kind: "resistor", nodes: ["p", "gnd"], resistanceOhm: 1 },
    { id: "I", kind: "current-source", nodes: ["gnd", "p"], currentA: 0,
      waveform: { kind: "pulse", low: 0, high: 1, delayS: 0,
        riseS: 0, highS: 0.05, fallS: 0, periodS: 0.1, count: 10 } },
  ],
});
const r = await a.pi().circuit(circuit).domain("time").initial("steady")
  .time({ stopS: 0.6, sampleStepS: 0.01 }).run();
a.check({ name: "Правый фронт в 0.5 s", actual: r.voltage(circuit.port("p")).at({ timeS: 0.5 }),
  target: 1, tolerance: 1e-10, unit: "V" });
```

**Исправление:** согласовать идентичность/локальную координату события и явные левое/правое значения. Не исправлять произвольным большим epsilon: левый предел непосредственно перед фронтом должен оставаться левым. Учитывать delay, номер периода и окончание count; не создавать большой развёрнутый список всех событий.

**Приёмка:** отдельные Rust-ожидания слева/точно/справа от нескольких границ pulse и repeated PWL (включая несовпадающие начальное/конечное значения), production DSL на R=1 Ω, событие на границе continuation, окончание повторов. Проверять независимо заданные 0/1 и ожидаемые времена. Текущий тест `discontinuous_current_and_repeated_pulse_pwl_do_not_smear_between_output_samples` использует тот же `Waveform::sample` как oracle и исключает несколько точных границ; этого недостаточно. Оставить существующие проверки и добавить независимые, включая точные границы.

## E2 — P2: бюджет continuation рассчитан от нуля

Место: `native/analyze/src/electrical/network.rs:269–276`.

Admission оценивает число отсчётов как `ceil(stopS / sampleStepS) + 2`, хотя continuation выводит только `[finalState.timeS, stopS]`. Более поздний корректный расчёт с мелким выводом отвергается по лимиту точек/памяти, даже если новый интервал мал.

Например, для той же постоянной R=1 Ω / I=1 A сети:

```js
const first = await a.pi().circuit(circuit).domain("time").initial("steady")
  .time({ stopS: 1, sampleStepS: 1 }).run();
const next = await a.pi().circuit(circuit).domain("time").initial(first.finalState)
  .time({ stopS: 1.001, sampleStepS: 1e-6 }).run();
```

Новый интервал содержит около 1001 отсчёта. Admission оценивает свыше миллиона, поэтому отдаёт `NETWORK_BUDGET` раньше корректной проверки/использования состояния. В примере circuit должен иметь постоянный источник, без pulse из E1.

**Исправление:** рассчитывать output budget по длительности нового интервала после безопасного подтверждения начального времени/совместимости состояния. Не доверять произвольному `timeS` из неподтверждённого JSON и не выделять state-sized массивы до ограничений. Матрица и остальная память по-прежнему учитываются полностью.

**Приёмка:** постоянная сеть выше завершается с правильной возрастающей осью 1…1.001 s и конечным временем; такой же genuinely большой новый интервал отклоняется; подмена/чужое состояние и stop≤start продолжают отклоняться. Не повышать общий лимит 100000 ради обхода ошибки.

## E3 — P2: частотный массив выделяется до admission

Место: `src/analyze/analysis-dsl/electrical-executor.ts:38`; схема `frequency.points` ограничена только положительным целым.

`Array.from({ length: pc.frequency.points }, ...)` исполняется до вызова Rust. Проверка 100000 точек/портовых решений и `maxMemoryMiB` в Rust происходит уже после создания/передачи массива. Например, разрешённый схемой запрос points=1000000000 способен израсходовать память процесса до штатного `NETWORK_BUDGET`. При этом заявленное ограничение размера входа ещё не применено. Process timeout не заменяет проверку размера до выделения.

**Исправление:** ограничить число частот и произведение частоты×порты на TS-границе до Array.from/сериализации, с согласованными правилами native admission. Нативную проверку сохранить для прямого addon-входа. Не вводить ещё один пользовательский DSL. Проверку размеров сделать безопасной и для очень больших целых; при недопустимой постановке возвращать контролируемую диагностическую ошибку.

**Приёмка:** большой points отклоняется до материализации частот; допустимые linear/log и frequencyHz продолжают работать, лимит с несколькими портами учитывается. Регрессия должна проверять раннюю валидацию без реального гигантского выделения памяти. После отказа следующий небольшой расчёт работает. Отдельно сохранить проверки memory budget в native.
