## 9.1. Путь DC → тепло на TPS63060DSCR

Путь: `a.dc()` (P5, `native/analyze/src/dc/system.rs`) → `dc.lossMap` → `a.thermal().losses(...)` (`thermal-loss-transfer.ts`). Высокочастотный экстрактор P7 в нём не участвует: DC-расчёт идёт за 0,8–1 с, 294 МиБ.

Отказ `THERMAL_LOSS_TRANSFER` «Loss map has uncomputed physical domains» (`thermal-loss-transfer.ts:14`) — правильный. DC считает только домены меди, до которых доходят объявленные контакты (источники, нагрузки, двухвыводные компоненты, металлизация), остальные выдаёт как `excluded_domains`; перенос отказывается подставлять за них ноль.

| Сценарий | Исключённые домены (цепь: площадки) | Итог |
|---|---|---|
| M4 (этап 0): U1 как `ic`, источники J1 и U1.9/7, нагрузки U1 VIN и J2 | SW1 (L1.1, U1.1), SW2 (L1.2, U1.10), FB (C7.2, R1.2), VAUX (C6.1, U1.6), PG (J3.1, на TOP и BOTTOM) — 6 из 12 | отказ переноса |
| M4b: плюс L1 `inductor` (DCR 0,03 Ом), R1 `resistor` (1 МОм), нагрузка-порт U1.10 → U1.1 2,5 А (ток катушки возвращается микросхемой с SW2 на SW1) | VAUX (C6.1, U1.6), PG (J3.1, оба слоя) — 3 из 12 | DC `complete`, перенос — тот же отказ |

Подставить ноль за SW1/SW2 было бы ошибкой: через них идёт ток катушки (2–3 А). Объявленный путь через L1 эти домены включает.

**Недостающий стык (назван):** у DSL нет способа объявить домен меди без постоянного тока. Для VAUX (только конденсатор C6 и вывод U1.6) и PG (вывод J3.1) ток по постоянному току равен нулю по схеме, но доказать это экстрактор не может: на цепи могут быть необъявленные компоненты. Поэтому на реальной плате с любыми «тихими» цепями перенос отказывает всегда. Варианты (решение за пользователем):

1. Явное утверждение в сценарии, например `.idleNets([net('VAUX'), net('PG')])` у `a.dc()`: такие домены входят в карту с нулём и записью «ноль по утверждению пользователя», результат `conditional`.
2. Тепловой расчёт принимает карту только по включённым доменам, исключённые остаются без тепла с явным списком, результат `conditional` (слабее: ошибку с SW1/SW2 из M4 он бы пропустил).
3. Оставить отказ; M4 — названный отказ.

Вторая мелочь сценария: двухвыводные `inductor`/`resistor` в DC принимают только сопоставление выводов по умолчанию (`UNSUPPORTED_DC_MODEL` при `pins`).

## 9.2. Запись о зависимости P10 от P7

`autonomous-decisions-2026-11-15.md`, строка 17, причина: «связь на плате требует P8/P7 на реальных платах». Для однонаправленной передачи DC-потерь (M4) это неверно: нужен только P5 DC; блокирует отказ по исключённым доменам, а не P7. Для электротепловой связи на плате (P10 с пересчётом R(T)) зависимость от P8 остаётся. Запись уточнена.

## 9.3. Реализация idleNets

Решение пользователя: вариант 1 из 9.1. Только TS, Rust не менялся (mesh исключённых доменов уже есть в отчёте нативного DC; `compactMesh` теперь сохраняет узлы и треугольники idle-доменов, а не только участвующих).

- DSL: `a.dc().idleNets([net('VAUX'), net('PG')])` (`schema.ts`, `spec-doc.d.ts`, `dsl-reference.md`); только `net`-селекторы, не для `conductor`.
- Семантика (`dc-executor.ts`): исключённый домен, вся медь которого (по `sources[].net` его `source_paths`) принадлежит idle-сетям, получает нулевые потери по всем треугольникам: `solution.idle_domains[{domain_id,layer,nets,loss_w}]`; в `lossMap` значения и срезы добавлены в конец, `data.idleDomains`; валидность `lossMap` `conditional`, причина «zero DC current asserted by the scenario for nets …». `voltageMap` и `currentDensityMap` idle-домены не покрывают (`excludedDomains` у них прежний). Без опции результат не меняется (проверено паритетом ниже).
- Отказы: `DC_IDLE_NET_CARRIES_CURRENT` (домен сети входит в расчёт), `DC_IDLE_NET_UNKNOWN` (нет на плате или нет треугольников; несуществующее имя может быть отвергнуто раньше слоем селекторов как `INVALID_CONFIGURATION`), `DC_IDLE_NET_MIXED_DOMAIN`. Исключённые домены вне `idleNets` по-прежнему отвергаются переносом.
- Перенос (`thermal-loss-transfer.ts`): `idle_domains` принимаются только с нулевыми `loss_w`, нулевые записи остаются в `heat`, `conditional` и причина доходят до `validity.reason` теплового результата и `lossTransfer.idleDomains`.
- Тесты: `tests/pcb-analysis-dc-idle-nets.test.ts` (4: принято и conditional с нулём; без опции без изменений; отказы; перенос), `pcb-analysis-dc*` 51 pass, `analysis-dsl` 31 pass, `pcb-analysis-thermal.test` 10 pass, typecheck чист.
- M4c (M4b + `idleNets VAUX, PG`, `M4c-dc-thermal.js`, `M4c/`, `M4c.log`): DC `complete`, idle-домены domain-000002 (PG, TOP), -000007 (VAUX, TOP), -000010 (PG, BOTTOM), перенос потерь проходит. Тепловой шаг сначала требует `.inputPolicy({cadFill:'snapshot'})` и у `thermal()` (CAD-заливка с неизвестной свежестью, как у DC). Дальше отказ нативного теплового расчёта `Selected source/contact has no physical mesh overlap`: причина не в idle-доменах, а в трёх нулевых треугольниках-щепках площадью 6e-11..2.5e-10 мм² во включённых доменах (domain-000008 x2, domain-000000), чьи регионы не пересекают тепловую mesh. Эксперимент (`M4c-zero-sliver-dropped-experiment/`, отладочный отброс нулевых записей не-idle, из кода убран): шаг завершается, подводимая мощность 0,02247 Вт (медь 0,02189 + переходные отверстия 0,00058), температура по `temperatureMap` 25,62..28,05 degC, валидность `conditional` с причиной idle. Решение по щепкам (нулевые записи тепла без перекрытия пропускать в нативном `target_weights`/переносе) не принято, это отдельная правка вне `idleNets`.
- Паритет (правило 11): купон 10 мм при 100 МГц `s9` против `A-defaults` через `cmpS.mjs`: побитово (`bitwise:true`, maxAbsDS 0), `parity-coupon-cmp.log`; TPS band-step 100 кГц (путь манифеста без бюджета) против `s72r-100000`: 7001 число, различий 0 (кроме времени и памяти), `parity-tps-cmp.log`.

## 9.4. Нулевые источники тепла (решение пользователя)

Записи меди с мощностью ровно 0 остаются в проверяемых данных переноса (сверка с картой потерь, проверка треугольников), но не передаются тепловому решателю как источники; их число — `provenance.zeroPowerEntriesSkipped`. Нагрев от них нулевой, температуры не меняются; причина — треугольники-щели 6e-11–2,5e-10 мм² в рассчитанных доменах не пересекают тепловую сетку и роняли решение («Selected source/contact has no physical mesh overlap»). Правка: `thermal-loss-transfer.ts`; тесты обновлены (`pcb-analysis-thermal` 15/15, `pcb-analysis-dc-idle-nets` 4/4, `analysis-dsl` 31/31, typecheck чист).

M4 (`debugging/p7-completion/stage9/M4d/`, сценарий `M4c-dc-thermal.js`, VAUX и PG объявлены без тока): `complete`, 5,7 с; тепло 0,02247 Вт (медь 0,02189, металлизация 0,00058); температура 25,62–28,05 °C; пропущено 1456 нулевых записей; результат `conditional` (снимок CAD, принятые коэффициенты, нулевой ток по утверждению сценария); проверка сценария `pass`. Все номиналы сценария — гипотезы.

Паритет купона и TPS после этой правки не перезапускался: перенос потерь в тепло не участвует ни в одном из этих путей (паритет после idleNets — в 9.3).
