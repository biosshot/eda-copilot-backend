# Интеграция анализатора в EasyEDA Copilot (рабочий план)

Дата: 2026-11-22. Бэкенд: ветка `feat/analyze` (HEAD `6b6a644`, P7-completion закрыт). Copilot: репозиторий `../easyeda-copilot`, ветка с RoutingBoardV2 (по указанию пользователя).

## 1. Цель

Агент Copilot пишет DSL-сценарий анализа по текущей разведённой плате, запускает его фоновой операцией, ждёт результата и получает статусы, числа и картинки (PNG), которые может сам посмотреть и показать пользователю. Схема та же, что у `make_pcb_layout`: бэкенд считает и рисует SVG, MCP сохраняет PNG и отдаёт пути.

## 2. Что уже есть

- Бэкенд экспортирует из корня `runAnalysisDsl({code, board, profiles, models}, {signal, timeoutMs, maxEntries, maxOutputBytes})` → `{status, reports, error}` (отдельный процесс, отмена, срок по умолчанию 45 мин) и `analysisDslDocumentation()` (справка `dist/analysis-spec-doc.d.ts`).
- DSL сохраняет только данные: результаты анализов (`DataValue`, карты `voltageMap`/`currentDensityMap`/`lossMap`/`temperatureMap` по треугольникам и слоям, частотные ряды, S/Z), `a.plot({title, kind: line|heatmap|table|eye|polar|bar, data, layer, atHz, atS})`, `a.check`, `a.log`, `a.report`. Картинок в продукте нет.
- Рендеры SVG/HTML есть только в тестовых хелперах: `tests/helpers/pcb-analysis-{dc,thermal,frequency,rlc,cross-section,line-losses,validation}-render.ts`.
- Layout: бэкенд отдаёт SVG как data URL (`src/pcb.ts`, `svgToDataUrl`), MCP растрирует (`mcp/src/tools/pcb/pcb-preview.ts`, `savePcbPreview`); фоновые операции — `operationManager` (`start`, `wait`, `operation_id`).
- Матрица готовности со временем, памятью и ожидаемыми статусами: `tests/pcb-analyze/p7-matrix.json`, итог P7 — `docs/analyze/evidence/p7-completion-summary-2026-11-21.md`.

## 3. Правила

1. Пороги приёмки решателей не меняются; интеграция не правит численные пути. Если правка всё же задевает решатель — паритет купона и TPS band-step (правило 11 P7-completion).
2. Тяжёлые прогоны по одному, `RAYON_NUM_THREADS=4 P7_HMATRIX_THREADS=4 CARGO_BUILD_JOBS=4`; прогоны и сравнения — дешёвым субагентам.
3. Картинка не добавляет утверждений: на каждой — статус достоверности, единицы, слой, частота/время и «физическая точность не проверена». Недоступные области (исключённые домены, урезанная ROI) рисуются как «неизвестно», не нулём.
4. Коммит — на этап, после отчёта и согласия пользователя; запись в `CHANGELOG.md` обоих репозиториев.

## 4. Этапы

### Этап 1. Рендер в бэкенде (`src/analyze/render/`)

| Шаг | Работа | Готово, когда |
|---|---|---|
| 1.1 | Перенести рендеры из тестовых хелперов в `src/analyze/render/` (DC, тепло, частота, сечение); тестовые HTML-отчёты переходят на продуктовый код | тесты `tests/pcb-analysis-*` проходят, отчёты те же |
| 1.2 | `renderAnalysisReport(output, board?)` → `{images:[{name, kind, analysis, layer?, atHz?, atS?, svg}], summary}`; детерминированный SVG, общая палитра и легенда, подпись статуса | тест на сохранённых `result.json` (M4, M7a, DC/thermal фикстуры), без новых прогонов |
| 1.3 | Автоматические картинки по результату (агенту не нужно вызывать `plot`): **обзор сценария** — контур, медь, порты/источники/нагрузки, путь канала, домены посчитанные / исключённые / `idleNets`, решённая ROI; **DC** — напряжение, плотность тока (пики отмечены), потери по слоям; **тепло** — температура по слоям, максимум отмечен; **сводка** — таблица результатов, статусы, коды отказов с причинами | по картинке на каждый вид на TPS DC→тепло (M4) |
| 1.4 | По частотным результатам и `plot()`: \|Z\| и фаза, S11/S21 в дБ (log-оси); для `pi()` — линия целевого импеданса и отмеченные превышения; `eye` — глазковая диаграмма; `table`/`bar` — таблица/столбцы; `heatmap` из `plot` — карта по сетке | картинки по M1 (сохранённый результат), M7a, eye-фикстуре |
| 1.5 | Карта Z0 вдоль канала: участки каскада раскрашены по своему Z0, стыки с оценкой \|dS11\| отмечены | картинка M7a/M7b |
| 1.6 | Экспорт: подпуть `./analyze` в `package.json` (`runAnalysisDsl`, `analysisDslDocumentation`, `renderAnalysisReport`, типы); корневой экспорт сохраняется | `npm run build`, импорт из `dist` в smoke-тесте |

### Этап 4. Скилл `pcb-analysis`

`mcp/docs/pcb-analysis/` по образцу `pcb-layout`, сборка в `skill/`.

- `SKILL.md`: порядок работы (сценарий → запуск → ожидание → чтение статусов и картинок → ответ); сначала обзор сценария, потом числа.
- Гипотезы: стек, материалы, номиналы компонентов, источники и нагрузки — из проекта или у пользователя; предположенное агент называет в ответе.
- Точность: «числа проверены на внутреннюю согласованность (невязки, пассивность, сходимость), но не на точность; для сравнения вариантов и порядка величин, не для приёмки». Процентов не писать, пока нет этапа 6.
- Время и память из матрицы: DC и тепло — секунды; канал каскадом ~30 с; канал с возвратом 15–20 мин; pi() на TPS ~45 мин; pi() на больших платах по всей сетке — больше часа (начинать с одной частоты); пик до ~4,2 ГиБ; тяжёлое — по одному.
- Что делать при отказах: `LOCAL_MIXED_FOIL_BAND` → сузить полосу до названной максимальной частоты; `LOCAL_DEADLINE` → меньше точек / одна частота / больше срок; `THERMAL_LOSS_TRANSFER` (исключённые домены) → `idleNets` для тихих цепей; `CHANNEL_RETURN_UNRESOLVED` → сказать, что связь не моделируется; `PI_UNMODELED_BRANCH` → объявить модели деталей.
- Значения `complete` / `conditional` / `partial` / `unavailable` для пользователя.
- Примеры: `tests/pcb-analyze/*/p7-matrix-*.js`, `dc.js`, `thermal.js` (с пометкой, что номиналы — гипотезы).

### Этап 5. Проверка в EasyEDA

На реальном проекте: TPS DC → тепло, канал BandAmp RF_IN, pi() TPS на одной частоте. Агент сам пишет сценарий, запускает, ждёт, показывает картинки и правильно пересказывает статус. Отчёт с картинками.

### Этап 6 (необязательный). Цифра точности

Эталонные проверки на купонах с аналитикой (DC-сопротивление дорожки, микрополоска Z0, пара плоскостей) → в скилле «на этих случаях расхождение X %». Только по решению пользователя.
