# Следующее задание: полный слой Analysis DSL и документация

Дата: **2026-10-22**. Основание — решение пользователя: следующим функциональным этапом сделать DSL по образцу PCB Layout, а не DC-решатель. Полный интерфейс означает полный согласованный язык описания анализов, **не реализацию всех вычислительных методов**. Текущее ревью сетки: [M1/M2](../../evidence/conduction-mesh-review-2026-10-22.md).

## Цель и результат

Добавить в `eda-copilot-backend` вход для JS-сценария, типизированные функции/описания/builders принятого Analysis DSL и самостоятельный файл деклараций-документации `spec-doc.d.ts`. Сценарий использует привычный JS, globals и `await`, создаёт конфигурации всех согласованных анализов; запуск конкретного анализа проходит через отдельную границу исполнителя.

В качестве образца прочитать `src/pcb-layout/pcb-layout-dsl/spec.ts`, `spec-doc.d.ts`, `scripts/copy-assets.mjs`, сборку/публичные entry points и существующие проверки DSL. Располагать новый слой в `src/analyze` (например, `analysis-dsl/`); не создавать пакет, репозиторий, собственный язык/грамматику или внешнюю зависимость на готовый анализатор. Не переносить весь PCB Layout builder в универсальный framework.

После этапа модель и человек должны иметь возможность прочитать один актуальный файл API, написать корректный сценарий и получить понятные ошибки конфигурации/отсутствующего решателя. Синтаксис и семантика JS не заменяются собственным AST-интерпретатором.

## 1. Источник пользовательского контракта

Обязательны:

- [dsl-reference.md](../../reference/dsl-reference.md) — полный перечень форм и результатов;
- [dsl-working-contract.md](../../reference/dsl-working-contract.md) — модели, ports, SI timing, данные;
- [dsl-scenario-decisions.md](../../reference/dsl-scenario-decisions.md) — принятые сокращения/сценарии;
- [dsl-components-simple.md](../../reference/dsl-components-simple.md) — распределение нагрузки/возврата и ручные значения;
- [dsl-board-scenarios.md](../../reference/dsl-board-scenarios.md), [dsl-data-matrix.md](../../reference/dsl-data-matrix.md) — примеры и покрытие.

Сохранить вариант B: `analysis({ board })` содержит snapshot и отчёт; физические параметры и режимы принадлежат конкретному builder. Не возвращать `a.assign`, обязательный converters, `.solver("openems")`, отдельный DDR solver, старые `transmitter/receiver/aggressors` или `.channel()` вместо `.channels()` в SI. `a.differential()` — описание пары; `timing()` — метод результата SI. Не добавлять ранее отклонённый механизм проверки двойного учёта моделей.

Перед кодом составить краткую таблицу покрытия: публичное имя → сигнатура → builder/описание/отчёт/результат → что выполняется сейчас, что требует будущего исполнителя. Если документы противоречат друг другу, применять поздние подтверждённые решения и исправлять устаревший пример. Новые предметные возможности не придумывать.

## 2. Вход сценария и граница MCP

- Сделать асинхронный runner, условно `runAnalysisDsl({ code, board?, profiles?, models? }, options)`. Финальное имя согласовать со стилем существующих entry points; не вводить несколько равнозначных входов.
- Исполняемый текст — JavaScript с функциями, переменными, ветвлениями и `await` в сценарии. TypeScript declarations нужны документации/IDE/проверке примеров. Не обещать приём TS-аннотаций в строке и не добавлять runtime-транспайлер без отдельной необходимости.
- Runner предоставляет согласованные globals. Ресурсы приходят явно; не искать board/stackup/materials автоматически в чужом чате, CAD или сети.
- Сохранять файл/строку/колонку пользовательского кода в синтаксических и runtime-ошибках, с поправкой на служебную async-обёртку.
- Один вызов runner соответствует одному сценарию. Каждая `.run()` формирует целостную задачу конкретного анализа, а не отправляет отдельный MCP-запрос от LLM. Последующий JS может использовать настоящий результат предыдущего анализа.
- Не обещать заранее собрать весь произвольный JS в один JSON: ветвления и `evaluate` могут зависеть от результатов. Callback исполняется на JS-стороне; функции и Promise не сериализуются в native-задачу.
- MCP-совместимый выход — сериализуемый отчёт, диагностика и описания/ссылки артефактов. API и builders не должны зависеть от MCP-session или транспорта. Не менять внешний MCP-сервер/плагин/CAD в этом задании; подготовить библиотечный вход для его будущей обёртки.
- Не экспортировать в контекст `process`, `require` и произвольный файловый/сетевой доступ. Не объявлять `node:vm` полноценной защитой от недоверенного кода. Deadline/abort всего сценария должен реально прекращать исполнение, включая цикл после `await`; учитывать это при выборе изолированного выполнения, используя существующие проектные механизмы. Не создавать новый общий compute-runtime.

## 3. Полный набор описаний и builders

Реализовать создание конфигураций для согласованных `geometry`, `dc`, `pi` (AC/transient), `thermal`, `electrothermal`, `impedance`, `tdr`, `si`, `eye`, `emi`, `em`, `networkParameters`. Реализовать синтаксическое описание вспомогательных объектов: selectors/ports, channels/differential, stackup/material/model/component descriptors, conductor/line/circuit/thermalNetwork, network/connect, scene/antenna, варианты — только в формах принятого справочника.

- Builders неизменяемые; повторный setter заменяет раздел, а не незаметно сливает его. Переданная конфигурация фиксируется для запуска; последующая мутация пользовательских массивов не меняет выполняемую задачу.
- Отдельные анализы не наследуют параметры друг друга. Один `board` можно использовать многократно; исходные данные не мутируются.
- Проверять известные имена полей, типы, единицы, обязательные разделы и взаимоисключающие режимы. Нельзя поддержать «полный DSL» через `any`/универсальный Proxy, который принимает любое имя метода и любой объект.
- Проверять ссылки на предоставленную плату/ресурсы, где это возможно без физического расчёта. Неоднозначный pad/net/port не выбирать молча. Boardless-конфигурация не требует платы, если принятый метод допускает её отсутствие.
- Компоненты задаются массивом с `designator`; явно заданные группы пинов не дополняются автоматически. Типы токов и возвратов соответствуют принятому правилу остатка/equal. Физический расчёт и автоматическое извлечение моделей по этим назначениям в этот этап не входят.
- Внутренние domain-модели, RoutingBoardV2 и уже существующие профильные типы переиспользовать через адаптеры. Отличие удобного пользовательского имени от внутреннего snake_case допустимо; второй независимый контракт платы не создавать.
- `.prepare()` может вернуть структурную диагностику и отсутствие исполнителя/непроверенные физические требования. Успешная проверка структуры не называется физической готовностью. `.run()` выполняет её автоматически; `await builder` ничего не запускает.

## 4. Исполнители и методы, которые ещё не считают

Сделать небольшую внутреннюю границу диспетчеризации «вид анализа + конфигурация → Promise результата», независимо от runner и MCP. Точные структуры определить по принятому API; не раздувать её в систему плагинов.

- В production пока нет DC/PI/thermal/SI/EM решателей. Их `.run()` возвращает явную типизированную ошибку `ANALYZER_NOT_IMPLEMENTED` (или единое имя в стиле проекта), а не пустой успешный результат/ноль/поддельную карту.
- Текущие import/geometry/conduction operations остаются внутренними. Не выдавать `prepareAnalysisGeometry` за весь пользовательский `a.geometry()` со всеми DRC-проверками, а `prepare-conduction` — за DC.
- Подставной исполнитель допустим только в тестах и должен быть явно тестовым. На нём проверить `await`, зависимые вызовы, результаты, check/plot и передачу задач. Не включать mock solver в production defaults.
- В `spec-doc.d.ts` описать полный результат каждого метода, включая `si.timing(options)` и операции над данными. Не реализовывать здесь timing extraction, eye calculation, S-преобразования, математику оптимизатора и другие вычисления только ради существования метода.
- `sweep/solve/optimize` и `evaluate` должны быть полностью описаны/типизированы. Для sweep допустим простой обход заданных values с callback на JS-стороне. Поиск/оптимизацию без готового алгоритма явно оставить недоступными; не подменять их фиктивным вызовом callback один раз. Любое отличие статуса поддержки видно в таблице API.

## 5. Отчёт, check и plot

- Общий механизм `check/log/plot/report` реализуется без физики. `check` записывает pass/fail/unknown и **не бросает исключение из-за невыполненного условия**; следующая строка выполняется.
- Неизвестное/неполное значение не становится нулём или успешной проверкой. Единицы/область валидности сохраняются. Ошибку программирования/запуска отличать от провала численного условия.
- `plot` регистрирует типизированное описание визуализации и переданные данные/ссылки. Новый движок графиков, интерфейс просмотра и полноценный рендер всех полей не входят в этап. Нельзя возвращать ссылку на несуществующий файл.
- Не копировать в каждую запись отчёта целый board, сетку и все модели. Сохранять воспроизводимые ссылки/идентичность контекста; ограничить журнал/вывод сценария понятным лимитом.
- При ошибке запуска вернуть/сохранить уже накопленную диагностику вместе с ошибкой; не маскировать её успешным отчётом.

## 6. Файл документации и поставка

- Создать самостоятельный `spec-doc.d.ts` по образцу PCB Layout: globals, интерфейсы, overloads/unions, JSDoc с единицами, default semantics, ошибками и небольшими примерами. Не оставлять ссылки на недоступные потребителю внутренние типы.
- Он должен соответствовать реализованному словарю DSL, отдельно обозначая отсутствие физических исполнителей. Исправить противоречия в рабочих Markdown-примерах, но не переписывать историю исследований целиком.
- Подключить новый файл к сборке/упаковке рядом с существующим `dist/spec-doc.d.ts` под отдельным analysis-именем; не перезаписывать PCB-документацию. Добавить удобный библиотечный способ получить Analysis DSL documentation по стилю проекта.
- Минимально экспортировать runner, его вход/выход и документацию. Общую предметную API-реализацию держать независимо от runner, чтобы прямой JS-вызов можно было открыть позднее без переписывания. Публикация большого нового standalone API не требуется сейчас.
- Полные примеры должны объявлять все свои ресурсы или явно получать их через контекст. В справочнике не оставлять «исполнимый» пример с необъявленными `power`, `consumer`, `dataPattern` без пояснения.

## 7. Проверяемые сценарии и условия приёмки

1. Таблица покрытия включает весь согласованный API. Все публичные имена/сигнатуры из документации согласованы с runner/builders; неизвестный setter отклоняется. Отдельно проверить взаимозаменяемые старые формы, которые были исключены пользователем.
2. Примеры USB, CAN, MCU/DC-DC/дисплей, RF-усилитель, DDR-шина, EMI с внешним возбуждением, thermal/радиатор и антенна проходят проверку типов и структур конфигураций без реальной симуляции. Это проверка языка, не сертификат поддержки физики.
3. Один сквозной тестовый сценарий с injected executor: первый результат используется во втором расчёте; независимые builders не обмениваются параметрами; callback остаётся в JS; задачи содержат ожидаемые ресурсы. Один production-сценарий доходит до понятной ошибки отсутствующего решателя.
4. Проверены snapshot/mutation, повторные setters, отсутствие implicit defaults, неизвестные ссылки, пропущенные обязательные поля, неверные единицы/режимы. Не использовать snapshot-only tests вместо содержательных отрицательных сценариев.
5. `check` с fail и unknown не прерывает следующую строку. `plot/report` сериализуемы, корректно сохраняют validity, не фабрикуют численные результаты/артефакты.
6. Syntax/runtime ошибки указывают пользовательскую строку. Бесконечный цикл до и после `await` прекращается по deadline/abort; после него новый сценарий выполняется. Сценарии не разделяют mutable globals. Не полагаться только на `Promise.race` для остановки зависшего JS.
7. Typecheck/build и профильные DSL/package tests проходят. Установленный архив содержит оба документа DSL и запускает реальный новый runner. Изменения упаковки не ломают PCB Layout/native process worker. Для чисто TS/документального этапа не требуется повторно считать весь медный/mesh-корпус без изменения native-кода.
8. Добавить `analysis-dsl-verification.md`: фактический API, статусы возможностей, команды/результаты и оставшиеся ограничения. Обновить architecture map, README и CHANGELOG. Вернуть изменения валидатору без самостоятельного коммита и без перехода к DC.

## Границы

Не реализовывать физические решатели, FEM matrix assembly, новый mesh/refill, извлечение моделей, загрузчики IBIS/SPICE/Touchstone, каталог материалов, GPU, автоподбор компонентов, UI графиков или внешнюю MCP-интеграцию. Не менять принятый пользовательский DSL ради удобства заглушки. Не создавать новую библиотеку/репозиторий и не публиковать пакет.

После приёмки этого этапа следующее задание — **DC-решатель и его подключение к уже существующему DSL**. Полный языковой слой не означает, что все анализаторы уже работают.
