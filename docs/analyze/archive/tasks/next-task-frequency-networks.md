# Следующее задание: частотные многопортовые модели — P6b

База: `38fb9a6`, [приёмка P6a](../../evidence/electrical-network-acceptance-2026-10-23.md). Реализовать следующий законченный блок P6 из [общего плана](../../plans/implementation-plan.md), затем передать на ревью. Не переходить самостоятельно к извлечению PCB/P7, board PI/P8 или SI.

## 1. Что пользователь получит

Через существующий DSL можно передать заданную частотную модель, получить её S/Z/Y-параметры, соединить несколько моделей и рассчитать общую сеть. Примеры: каскад аттенюаторов, заданный канал с отражениями, модель усилителя с S21≠S12, сеть с несколькими связанными портами.

Это **заданные частотные модели**, а не автоматическое моделирование трасс/компонентов по PCB. Геометрическое извлечение, transient импортированных S-параметров, fitting/FFT, TDR и полноценный RF/SI останутся последующими этапами. P6b не объявляет весь P6 завершённым.

Обязательный production-путь: `models`/локальный Resource (в том числе созданный через `a.model`) → `a.network` → при необходимости `a.connect` → `a.networkParameters().run()` → Rust → комплексные DataValue → check/plot/report. Не создавать новый runner или новый DSL.

## 2. Переиспользование и границы модулей

Прочитать AGENTS/CHANGELOG, `numerical-architecture.md`, актуальные `schema.ts`, `spec-doc.d.ts`, `context.ts`, `prepare.ts`, `executor.ts`, `electrical-executor.ts`, `native/analyze/src/electrical/`, direct-DSL fixtures и audits.

- TS: существующие immutable descriptors, resource catalog, структурная валидация, ранние ограничения размеров, транспорт и отчёт.
- Rust CPU/F64: строгая нормализация импортируемых данных, преобразования матриц, компоновка/решение частотной сети, численные проверки. Разбор Touchstone можно держать рядом с этим модулем; не заводить второй parser в test helper.
- Переиспользовать `faer`, комплексные операции/разреженное решение и runtime P6a там, где задачи совпадают. Не заставлять FEM DC или временной RLC solver работать через S-матрицы. Внутренняя реализация может хранить небольшие плотные матрицы отдельных multiport-блоков; большая составная система должна иметь явный размер/бюджет.
- Один общий `.node`, существующие worker/process, deadline/cancel/report budget, DataValue transforms/check/plot/sweep. Без `compute-runtime`, GPU/F32 и внешнего симулятора.

Модель частотного блока должна быть пригодна для будущего результата извлечения P7: нормализованные порты, частоты, комплексные коэффициенты, reference impedances и validity/provenance. Не менять RoutingBoardV2 ради этого.

## 3. Поддержанный вход Resource

Не читать пути/URL из sandbox DSL или Rust. Host заранее передаёт данные через существующий `models`; launcher читает локальный файл и сохраняет его точное содержимое/hash. `source` — происхождение данных, а не команда загрузки. Не делать runtime network requests или поиск даташитов.

Зафиксировать один документированный поднабор `Resource.data` и валидировать его строго. Минимальная форма для этого этапа:

```ts
type Complex = { real: number; imaginary: number };
type FrequencyNetworkData = {
  format: "network-parameters";
  representation: "S" | "Z" | "Y";
  frequenciesHz: readonly number[];
  // parameters[frequencyIndex][outputPortIndex][inputPortIndex]
  parameters: readonly (readonly (readonly Complex[])[])[];
  // Для S обязательно; порядок/ключи соответствуют Resource.ports.
  referenceOhm?: number | Readonly<Record<string, number>>;
  referenceTopology: "common";
  nature: "passive" | "active" | "unspecified";
};
type TouchstoneNetworkData = {
  format: "touchstone";
  content: string;
  referenceTopology: "common";
  nature: "passive" | "active" | "unspecified";
};
```

Обе формы находятся внутри Resource с `kind: "network"`, `id`, **упорядоченным** `ports: string[]`, `data` и необязательными существующими source/validity/analyses. Порядок Resource.ports определяет индексы матрицы/портов файла; никакой сортировки по алфавиту. Дубли, неверные размеры, пустые имена, NaN/Infinity и несогласованные данные отклоняются. Для Z/Y единицы — Ohm/Siemens; referenceOhm входного S нельзя трактовать как физические резисторы нагрузки. Неоднозначное лишнее поле referenceOhm у нормализованного Z/Y отклонять либо явно запретить схемой.

`referenceTopology:"common"` — явное ограничение на модели с общей опорой внутри блока. Произвольные раздельные возвратные контакты, mixed-mode и привязка к PCB-площадкам пока не поддерживаются; не угадывать их. В `a.network` все порты ресурса должны быть однозначно представлены именами DSL. Частичную карту отклонять: отсутствие порта не означает согласованную нагрузку.

### Расширение существующего `a.model()`

В рамках P6b расширить фабрику `a.model()` входом Resource с `kind: "network"` и обеими описанными выше формами data: `network-parameters` (S/Z/Y) и `touchstone`. Сохранить все существующие варианты LocalModel и их валидацию. Это целевое расширение этапа, а не утверждение о поддержке в базе `38fb9a6`.

- `a.model()` проверяет описание и возвращает неизменяемый объект модели в той же универсальной форме Resource, без регистрации экземпляра сети, запуска solver или загрузки данных. Обязательные поля не подставляются из скрытых defaults. Результат напрямую принимается `a.network({ model, ports })`; публичная TypeScript-сигнатура должна сохранять тип сетевого ресурса без casts со стороны пользователя (например, через перегрузку).
- Прямой Resource в `a.network` и ресурсы каталога `models` остаются допустимыми. Фабрика и прямой путь используют общую структурную валидацию и ранние лимиты; обойти проверки пропуском `a.model()` нельзя. Численная проверка пассивности, преобразования и Touchstone parser остаются в общем production-пути Rust, без второго solver/parser в фабрике.
- Одна модель переиспользуется несколькими `a.network`, каждый вызов создаёт отдельный экземпляр. `a.model` описывает поведение, `a.network` — экземпляр и mapping, `a.connect` — соединения, `networkParameters` — расчёт.
- Не добавлять специальный `kind: "ideal-attenuator"`, генератор матриц аттенюатора или fluent-builder модели. Пользователь может вычислять коэффициенты обычным JavaScript. Универсальный объект остаётся пригодным для аттенюаторов, усилителей, фильтров и любых поддержанных многопортовых данных.
- В примерах и связанных fixtures использовать ключ `models.electrical.attenuatorPad`, подпись **Attenuator Pad** и понятный model id вместо неоднозначного `models.electrical.pad`. Это имя конкретного ресурса, не новый тип модели и не контактная площадка PCB; отдельное поле display name в контракт не добавлять.

## 4. Ограниченный Touchstone

Использовать первоисточник [IBIS Touchstone 2.0 specification](https://www.ibis.org/touchstone_ver2.0/touchstone_ver2_0.pdf), разделы option line, port count/order, reference и network data. Он описывает также исходный формат 1.0. Проверить по документу порядок коэффициентов, а не опираться на симметричный пример. Никакой код стороннего simulator не подключать.

Обязательный поднабор: **S-параметры**, версии 1.0 и 2.0; RI/MA/DB; Hz/kHz/MHz/GHz; комментарии/переносы и стандартные defaults option line; полный single-ended matrix. В 2.0 — `[Number of Ports]`, `[Number of Frequencies]`, `[Two-Port Data Order]`, `[Reference]`, `[Matrix Format] Full`, `[Network Data]`, `[End]`. Порядок 2-port должен учитывать 21_12/12_21; для ≥3 портов — установленный стандартом порядок. DB означает 20log10 модуля, углы — градусы. Эти правила брать непосредственно из [спецификации IBIS](https://www.ibis.org/touchstone_ver2.0/touchstone_ver2_0.pdf).

Версия 1.0 получает число портов из явного Resource.ports; версия 2.0 обязана совпасть с ним. Принятые стандартные defaults сохранять в нормализованном отчёте. В этом этапе не обещать весь стандарт: Z/Y/H/G именно **в файлах**, noise blocks, triangular matrices, mixed-mode, 1.1/2.1 и неизвестные физически значимые keywords отклонять с точным объяснением. Нормализованный JSON выше отдельно поддерживает Z/Y в физических единицах. Information-блоки можно явно пропустить как метаданные, задокументировав это.

До крупных выделений ограничить bytes текста, число портов/частот, произведение F×N² и размеры результирующей системы. Нельзя сначала split/развернуть неограниченный файл, а затем проверять лимит. Начальный поддержанный предел — до 16 портов на ресурс и до 100000 частот при более строгом общем лимите элементов/памяти; итоговые безопасные caps описать и протестировать. Числа из заголовков должны согласовываться с фактическими записями. Ошибка содержит resource id и строку/позицию, где возможно.

## 5. Математика и численные гарантии

### Представления и опорные сопротивления

Матрица результата имеет row=out, column=in. Для S использовать power-wave convention с положительными вещественными, не зависящими от частоты referenceOhm, отдельно на каждом порту. Комплексные reference impedances пока отклонять. Отношение амплитуд S безразмерно; Z — Ohm, Y — S (Siemens).

Поддержать S↔Z↔Y и перенормировку S на заданные выходные referenceOhm, включая разные сопротивления портов. Считать через решения линейных систем, не явное обращение и не поэлементное преобразование. Диагональные нормировки при неравных reference нельзя переставлять местами как скаляры. Для S output referenceOhm явно задаётся существующим builder; это **новая нормировка**, а не перезапись метаданных исходной матрицы. Для Z/Y output reference не изменяет физическую сеть; неоднозначные лишние настройки диагностировать.

Нельзя принуждать каждую S-модель сначала стать Z или Y. Идеальный thru имеет корректную S-матрицу, но преобразование в конечную Z может быть сингулярным. Open/short также имеют представления с полюсами. Корректный S-ответ/соединение должны работать через волновые либо неявные V/I-отношения; запрос несуществующего конечного представления получает диагностику. Не добавлять gmin/потери, не заменять бесконечность большим числом.

Проверять residual и обусловленность/ранг используемых систем, показывать причину numerical failure. Если требуемая частотная точка не вычислена, нельзя вернуть успешную нулевую матрицу. На этом этапе допустим отказ всего запроса с указанием частоты, вместо нового сложного API частично успешных сетей.

### Полоса и интерполяция

Частоты нормализуются в Hz, строго возрастают, неотрицательны. DC-точку 0, если она явно есть в ресурсе, сохранить; существующий пользовательский frequency builder остаётся положительным. Не экстраполировать к DC или за верхнюю границу, не достраивать хвосты/причинность.

На исходных точках возвращать исходные значения с точностью преобразований. Между ними — один явно описанный метод комплексной линейной интерполяции по частоте: отдельно real/imaginary, в фиксированном нормализованном представлении/опорах. Не интерполировать wrapped phase или dB как универсальные физические величины. Для нескольких ресурсов допустимый диапазон — пересечение; одинаковые сетки не обязательны. Одна частотная точка модели позволяет считать только её, а не постоянную сеть во всей полосе. Запросы вне диапазона дают отказ.

Межточечные значения отмечать как интерполированные/conditional, с ресурсами и интервалами происхождения. До вычислений записать, где/в каком представлении выполнена интерполяция; для каскада сначала получить модели на общей запрошенной частоте, затем соединять. Различие интерполяции до/после преобразования не скрывать.

### Пассивность и активные модели

Для явно passive S проверять нормированную мощность на вычисляемых частотах (например, max singular value ≤1 с численным допуском). Проверка отдельных |Sij|≤1 недостаточна для многопортовой сети. Пассивность Z/Y проверять в эквивалентной корректной нормировке. Не проецировать данные на пассивное множество молча.

`nature:"active"` разрешает усиление и невзаимность. Не требовать S21=S12. `unspecified` не объявлять пассивным по названию файла. Пассивность в проверенных точках не доказывает причинность/устойчивость во всей полосе; временной отклик, устойчивость RF-усилителя и certification этим этапом не обещаются. Неверно помеченный passive ресурс должен получить явный диагностический отказ/непригодность до успешного check; сохранить вход без «исправления» коэффициентов.

## 6. Соединение сетей

Использовать существующий `a.connect({ networks, connections, ports })`. Соединение from/to — соединение положительных контактов пары и их возвратов, с согласованными знаками входящих токов; не считать его просто умножением S21. Разные исходные reference impedances не создают физического сопротивления на стыке, но должны корректно учитываться математически.

Минимальный обязательный класс: произвольные полные multiport-блоки, попарные соединения портов, несколько внешних портов, вложенная композиция; нельзя ограничить solver только произведением двух 2-port. На этом этапе каждый порт блока должен быть либо внешним, либо подключён ровно к одному другому порту. Неявные заглушки, незаданные нагрузки, многосторонние junction на одном порту и дубли внешнего alias отклонять. Нагрузку можно явно задать однопортовой моделью. Все блоки должны влиять на доступную внешнюю сеть; неподключённые скрытые части отклонять, не игнорировать.

Общие возвраты внутри ресурса объединяются согласно объявленной topology; глобальная referenceOhm не соединяет физические возвраты. Не вводить отдельный механизм «замены части модели», ранее отклонённый пользователем. Композиция работает только с явно заданными блоками.

Сохранять provenance каждого экземпляра: один Resource можно использовать в двух разных `a.network` и получить два устройства. Повтор handle одного и того же устройства не должен неявно клонировать его; пересечения nested-графов выявлять. При изменении модели, mapping, соединения, частоты или выходной нормировки старый результат остаётся immutable, cache не возвращает устаревшую матрицу.

`result.network` должен возвращать пригодный для дальнейшего `a.connect`/`networkParameters` descriptor с вычисленными значениями и сохранённой полосой/validity. Это не разрешение использовать его в transient без будущего временного представления. Если число сохранённых элементов превышает report budget, отказ явный; не выдавать handle на потерянный результат.

## 7. Пример целевого DSL

Модель **Attenuator Pad** можно задать прямо в DSL через `a.model()` или передать из host как `models.electrical.attenuatorPad`, Resource с двумя портами `p1/p2`. Например, два одинаковых отсчёта идеализированного согласованного аттенюатора на 1 и 2 GHz: S11=S22=0, S21=S12=0.5, reference=50 Ohm, `nature:"passive"`, common return. Это синтетическая модель, не параметры реального компонента. В Touchstone 1.0 она может быть задана так:

```text
! Attenuator Pad: synthetic matched attenuator, not measured hardware
# GHz S RI R 50
1 0 0 0.5 0 0.5 0 0 0
2 0 0 0.5 0 0.5 0 0 0
```

Сам сценарий хранится прямым JavaScript:

```js
const a = analysis();
const referenceOhm = 50;
const frequenciesHz = [1e9, 2e9];
const reflection = { real: 0, imaginary: 0 };
const transmission = { real: 0.5, imaginary: 0 };
const attenuatorModel = a.model({
  id: "my-attenuator",
  kind: "network",
  ports: ["p1", "p2"],
  data: {
    format: "network-parameters",
    representation: "S",
    referenceOhm,
    referenceTopology: "common",
    nature: "passive",
    frequenciesHz,
    parameters: frequenciesHz.map(() => [
      [reflection, transmission],
      [transmission, reflection],
    ]),
  },
});
const first = a.network({
  model: attenuatorModel, ports: { input: "p1", output: "p2" },
});
const second = a.network({
  model: attenuatorModel, ports: { input: "p1", output: "p2" },
});
const cascade = a.connect({
  networks: [first, second],
  connections: [{ from: first.port("output"), to: second.port("input") }],
  ports: { input: first.port("input"), output: second.port("output") },
});
const r = await a.networkParameters().network(cascade)
  .frequency({ startHz: 1e9, stopHz: 2e9, points: 101, scale: "linear" })
  .representation("S").referenceOhm(50).run();
a.plot({ title: "Передача каскада", data: r.parameter({ out: "output", in: "input" }).magnitude() });
a.plot({ title: "Отражение входа", data: r.parameter({ out: "input", in: "input" }).magnitude() });
a.check({ name: "S21 в исходной точке", unit: "1",
  actual: r.parameter({ out: "output", in: "input" }).at({ frequencyHz: 1e9 }).magnitude(),
  target: 0.25, tolerance: 1e-10 });
```

Для варианта с каталогом заменить объявление модели на `const attenuatorModel = models.electrical.attenuatorPad;`, передав тот же Resource из host. Оба способа должны давать одинаковый результат. При необходимости пользователь задаёт ослабление через `10 ** (-attenuationDb / 20)` вместо `0.5`, без специального типа аттенюатора.

Ожидаемый S21=0.25 следует из согласованных S11/S22=0. Для отражающих/невзаимных моделей такого произведения в общем случае недостаточно — это обязательно проверить отдельными тестами. Не добавлять `.db()` только ради этого примера: текущих magnitude/phaseDeg/real/imaginary достаточно. График dB при необходимости строит renderer с явной нормировкой и обработкой нуля.

## 8. Обязательные независимые тесты

### Парсинг и mapping

- Ручные нессиметричные 2-port данные с разными S12/S21 для 1.0, двух вариантов 2.0 order и RI/MA/DB. Восстановленные complex coefficients совпадают с заданными. Не использовать только thru/аттенюатор как oracle порядка.
- 1-port, ≥3-port с уникальными коэффициентами каждой позиции; неравные reference; units GHz→Hz; comments/line wrapping/defaults. Повреждённая длина записи, порядок ключей/версий, counts, дубли, неизвестные физические блоки, negative frequency/nonfinite, конфликт числа портов отвергаются.
- Большие заголовки/bytes/N²×F ограничиваются до крупных выделений. Испорченная модель не обходится переходом на другой parser или успешную прошлую версию.

### Математика

- Однопортовый R: S=(R−R0)/(R+R0), Z=R, Y=1/R; несколько R0. Open/short/thru: корректный S и контролируемая недоступность сингулярного преобразования.
- RLC-купоны из P6a: независимые формулы Z(f), перевод в S/Y и обратно; можно дополнительно сравнить с существующим MNA, но не делать его единственным оракулом.
- Неравные reference по портам; перенормировка туда/обратно; переименование/перестановка портов с ожидаемой перестановкой строк/столбцов. Имена и значения должны проверяться вместе.
- Два согласованных аттенюатора; затем отражающий каскад, где произведение S21 даёт неверный ответ. Проверить согласованность всего 2×2 результата, а не только transmission magnitude.
- Заданная активная невзаимная модель (например, S21=2, S12=0.01 с явно заданными отражениями) работает как active и не объявляется пассивной. Та же модель, ошибочно помеченная passive, выявляется.
- Passive multiport с каждым |Sij|<1, но max singular value>1, не проходит проверку пассивности. Нулевой/малый ответ проверять абсолютным физическим floor.
- Композиция ≥3-port, явная однопортовая нагрузка, nested composition, корректный ideal thru внутри каскада; отсутствие скрытого matched termination. Сингулярное соединение имеет диагностируемый отказ.
- Точные частоты, разные сетки/их пересечение, interpolation с известными affine complex данными, скачок wrapped phase около ±180°, single-frequency модель и выход за полосу. Проверка интерполяции отдельно от изменения reference.

Целевые допуски на хорошо обусловленных аналитических купонах: относительная ошибка ≤1e-8 либо абсолютный floor 1e-10 для безразмерного S и документированный floor в Ohm/Siemens для Z/Y. Остаток линейной системы — нормированный ≤1e-8. Проверять complex response, не только модуль. Для пассивности нужен отдельный численный допуск; не расширять его, чтобы принять заведомо активный пример. Round-trip не заменяет независимый oracle: два одинаково ошибочных преобразования могут обратить друг друга.

### Production и регрессии

Проверить расширение `a.model()` через публичные типы и production DSL: сетевые S/Z/Y и Touchstone ресурсы принимаются и передаются в `a.network` без casts; существующие локальные модели и их отрицательные проверки сохраняются. Сравнить расчёт одной модели через фабрику, прямой Resource и каталог `models.electrical.attenuatorPad`. Проверить неизменяемость результата фабрики и независимость от последующей мутации исходного объекта. Повреждённые размеры/порты, обязательные поля, nonfinite и лимиты не обходятся прямым Resource; физически неверная passive-модель не становится допустимой после фабрики. Включить прямой сценарий из раздела 7 и сохранить S21=0.25 в исходной точке.

Проверить публичный установленный пакет, два экземпляра одного ресурса, неточное/чужое mapping, immutable old result, reuse и инвалидацию, повторное использование `result.network`, report budget, timeout/cancel и успешный следующий запуск. Временные анализы импортированной табличной сети по-прежнему явно unsupported.

Сохранить E1–E3, M1 и D1–D3. Не менять физические inputs существующих DC/RLC-плат и не ослаблять их guards. Новые tests/helper не реализуют собственный parser/network solver вместо production.

## 9. Примеры, визуальные отчёты и корпус

Добавить прямые `.js` с тонкими launchers и проверяемыми resources. Набор должен содержать хотя бы: пассивный каскад с отражениями, невзаимный усилительный блок в полосе около 2 GHz, связанный multiport. Все числа синтетических ресурсов явно маркировать; исходные тексты/нормализованные таблицы хранить versioned рядом с тестами.

Дополнительно минимум два сценария в существующем корпусе, например `BandAmpV5` и `STM32G0_CAN_RS485`, через `--name network`. Проверить реальные обозначения выбранных входов/выходов/возвратов по fixture. Показать рядом явно заданную сетевую модель выбранного участка и её исходные допущения. Не называть низкочастотную реальную плату 2 GHz усилителем ради примера; синтетический RF-эталон существует отдельно. Не выдавать произвольные S-параметры за измерения/экстракцию этих плат. Новую физическую привязку модели к медной сетке сейчас не реализовывать.

Отчёт: source model ids/hashes, mapping и порядок портов, полоса, source/output reference, nature, interpolation/validity, выбранные коэффициенты, magnitude/phase и real/imaginary, checks. Общие оси для сравнения исходной/составной сети и разных нормировок. Отдельно показать ожидаемый fail и следующий выполненный check/plot. Никаких AC-карт токов PCB без расчётной модели геометрии.

Versioned audit вызывается launcher на текущем результате, проверяет ожидаемые case/model/port identities, исходные коэффициенты, нормировки, оси/units, complex эталоны, validity, проверки и реальные массивы графиков. Negative audit tests переставляют S12/S21, reference/ports, удаляют частоту/plot, подменяют active/passive и делают extrapolation. Все такие нарушения должны выявляться. Исторические удачные результаты не подставляются вместо отсутствующих.

Сохранять exact `.js`, resource bytes/hash, resolved inputs, source/native hashes, JSON/audit, wall time/peak RSS, HTML и screenshots в ignored debugging. Открыть итоговые отчёты и проверить обе страницы плат, passive/active графики, фазу, mapping/reference и expected fail→continue. Генерируемые артефакты не включать в коммит.

## 10. Порядок, исключения и критерии приёмки

Порядок внутри задания: нормализованный ресурс и source parser → преобразования/ренормировка/сингулярности → соединение моделей → production DSL/result → комплексные эталоны и direct examples → audit/visual QA. Это один этап с законченным пользовательским результатом.

Не реализовывать сейчас Touchstone export, смешанные дифференциальные режимы, IBIS/AMI, arbitrary SPICE, fitting/passivity repair/FFT/causality enforcement, transient импортированных моделей, PI/SI/EMI/thermal/full-wave, извлечение трасс/vias/PDN, GPU, отдельную библиотеку исполнения или новый board-контракт. Не добавлять инструмент для загрузки URL из DSL.

Этап принят, когда весь заявленный поднабор работает через существующий DSL, включая расширенный `a.model()` без регрессий локальных моделей, есть независимые complex эталоны и отрицательные проверки, корректный thru не теряется из-за сингулярной Z, unequal reference/mapping не путаются с нагрузками, ограничения и неизвестность не превращаются в successful zero, есть исполняемые прямые сценарии и проверенные отчёты. В актуальных примерах/fixtures/отчётах аттенюатор называется `attenuatorPad` / Attenuator Pad, старый ключ `models.electrical.pad` не используется. Отдельно документировать, что пассивность проверена только на заявленных точках, а temporal model не получена.

Исполнитель выполняет focused Rust/Node regressions, native build, typecheck/build, package checks и один итоговый прогон новых fixtures на итоговую версию. Старые большие корпуса повторять при влияющем изменении общего пути; иначе сохранить evidence и честную проверку source parity, без циклических повторов. Записать фактические команды/exit codes, tolerances, версии, бюджеты, hash/provenance и ограничения в `frequency-networks-verification.md`. Обновить `spec-doc.d.ts`, DSL reference, module READMEs, architecture map, experimental index и CHANGELOG. Передать на ревью; новый этап и автоматический коммит не делать.
