# Следующее задание: электрическое RLC-ядро через Analysis DSL

База: DC принят в `411b38d`, см. [приёмку](../../evidence/dc-acceptance-2026-10-22.md). Это первый законченный блок P6 из [плана реализации](../../plans/implementation-plan.md), далее называемый **P6a**. Выполнить реализацию и проверки, подготовить изменения к ревью. Не переходить самостоятельно к P7/P8 и следующим анализаторам.

## 1. Результат этапа

Пользователь задаёт линейную электрическую сеть обычным JavaScript DSL и получает:

1. DC-рабочую точку: напряжения, токи элементов, потери.
2. Комплексный входной импеданс заданных портов по частоте.
3. Переходные напряжения/токи при заданных источниках и скачках нагрузки, с контролем ошибки и продолжением из состояния предыдущего расчёта.
4. Численные проверки и читаемые графики в сохранённом отчёте.

Один Rust-модуль сборки электрической сети обслуживает эти режимы. Это существенный работающий этап, а не только схемы типов/заглушки. Реализовать production-путь DSL → существующий worker/process → общий Node addon → Rust → сериализуемый результат → check/plot.

**Граница:** сейчас сеть задаётся явно. Частотное извлечение сопротивлений, индуктивностей, ёмкостей и связей из PCB относится к P7. Полный PI по извлечённой PCB относится к P8. Нельзя назвать повтор DC-матрицы с произвольными L/C широкополосным анализом платы.

## 2. Что переиспользовать

Перед изменениями прочитать `AGENTS.md`, `CHANGELOG.md`, `src/analyze/README.md`, текущие `schema.ts`, `spec-doc.d.ts`, `prepare.ts`, `executor.ts`, `dc-executor.ts`, `execute-problem.ts`, `native/analyze/src/dc/`, тестовый launcher и direct-DSL fixtures.

- Существующие `a.circuit`, builders, `a.model`, описания источников/waveform, типизированные DataValue, check/plot/sweep.
- Существующий транспорт задач, отмену, process isolation, timeout/budget/report limits и один общий `.node`.
- Имеющийся `faer` и подходы к sparse solve, residual/balance diagnostics. FEM DC не обязан становиться MNA: общие небольшие функции выносить только при реальном совпадении задач.
- Прямые `.js`-сценарии, тонкий `.ts` launcher, audit текущего отчёта и локальные артефакты.

Численные алгоритмы — Rust, CPU/F64. TS отвечает за DSL, адаптацию, оркестрацию и отчёт. Не создавать `native/compute-runtime`, новый addon, отдельный публичный DSL или альтернативный scenario JSON. Не менять placement/F32.

## 3. Обязательный поддержанный поднабор

| Возможность | В этом этапе |
|---|---|
| `a.dc().circuit(c).run()` | Линейная рабочая точка |
| `a.pi().circuit(c).domain("frequency")` | `.frequency(...)` / `.frequencyHz(...)`, комплексный `impedance(port)` |
| `a.pi().circuit(c).domain("time")` | `.time(...)`, `.initial("steady")` и продолжение из совместимого `finalState` |
| Элементы | R, C с ESR/ESL, L с последовательным R, идеальные независимые V/I-источники |
| Простые модели | Те же R/C/L через `a.model` и `kind: "model"` с явным сопоставлением контактов |
| Возбуждения во времени | Существующие step, pulse, pwl, sine; конечные фронты, контроль точек смены формулы |
| Выход | Scalar/series, единицы, validity, diagnostics, численное качество, реальные данные графиков |

Не добавлять скрытые ESR/ESL и сопротивление источника. `ideal: true` означает явно принятую идеальность; заданные нулевые паразитики сохраняются. Неподдержанная модель/сочетание не должно незаметно превращаться в идеальный элемент.

В standalone circuit источники и нагрузки уже являются элементами: не добавлять к ним ещё раз board `.sources/.loads/.components`. Наличие платы в host input не означает автоматическое подключение её меди к явно заданному circuit.

## 4. Семантика до написания solver

Закрепить в документации и тестах, не вводя новый API там, где уже есть подходящий:

- `V = V(nodes[0]) - V(nodes[1])`; положительный ток элемента течёт от первого узла ко второму. Мощность по passive sign convention: потребитель положительный, отдающий источник отрицательный. Потери включают диссипацию, а не запасённую энергию L/C.
- Явный reference либо уже документированный узел `gnd`. Нельзя лечить плавающую/вырожденную сеть скрытым сопротивлением на землю или автоматически замыкать независимые опорные узлы.
- Источник с waveform во времени принимает **абсолютное значение** waveform, не сумму с `voltageV/currentA`. Для DC используются постоянные `voltageV/currentA`; для `.initial("steady")` — значения временных источников в начале расчёта. В отчёте эти постановки различены. Событие в t=0 имеет документированную одностороннюю семантику; противоречивые начальные ограничения диагностируются.
- Passive port только измеряет разность потенциалов. Объявление ещё одного порта не добавляет нагрузку, не меняет матрицу и не создаёт электрода.
- `current("elementId")` возвращает ориентированный ток известного элемента. У произвольной пары узлов без ветви нет однозначного «тока порта»: такой запрос unavailable с причиной, а не сумма всех соседних токов.
- Локальные R/C/L модели имеют документированные имена двух контактов; mapping должен быть полный и однозначный. Результат должен совпадать с непосредственным элементом.

### Частотный режим

Для `impedance(port)` считать driving-point Z: занулить независимые малосигнальные источники (идеальный V → нулевое напряжение, I → нулевой ток), приложить тестовый ток к выбранной портовой паре и получить комплексное V/I. Направление тестового тока и знак Z задокументировать; пассивный резистор должен дать положительное R.

Несколько портов рассчитываются как отдельные возбуждения одной сети; одинаковая частота допускает reuse факторизации с разными RHS. Объявленные порты не создают согласованных нагрузок. Постоянные 3.3 V источника — не AC-амплитуда 3.3 V.

На этом этапе не требуется новый интерфейс AC-возбуждений, `transfer`, автоматический поиск `resonances`, полная S/Z/Y-матрица или частотные `voltage/current` под неявным возбуждением. Для невычисленного метода сохранять unavailable/понятный диагностический результат. Нельзя подставлять ноль или DC-значение вместо частотного результата. Полезная частотная часть этапа — проверяемый Z(f), его модуль/фаза и вещественная/мнимая части.

### Переходный режим

Использовать неявное интегрирование с контролем ошибки. Допустимый начальный вариант — backward Euler с оценкой ошибки через удвоение шага; не внедрять несколько интеграторов ради выбора. Численное затухание метода нужно показать на RLC-тесте и уменьшать уточнением, не выдавать его за физический ESR.

`sampleStepS` управляет **выводом**, не является внутренним шагом интегратора. Внутренний шаг обязан разрешать динамику и breakpoints источников, включая конечные фронты/разрывы и повторы PWL/pulse. Ограничить число внутренних шагов и сохранённых точек; истощение бюджета не считается complete.

Нормирование ошибок напряжений, токов и уравнений описать через физические масштабы/допуски. Не сравнивать V и A одним безразмерным сырым epsilon. Существующие `.numerics` должны иметь документированный смысл либо явно отклоняться в неподдержанном сочетании; не игнорировать переданные значения. Начать с документированных внутренних масштабов, без набора новых публичных настроек solver.

`finalState` содержит необходимые напряжения C, токи L, физическое время и идентичность поддержанной модели. Продолжение — та же совместимая сеть/контекст, на общей временной оси: при начальном времени состояния t0 новый `stopS` означает абсолютный конец > t0. Фазы и pulse/PWL-события не стартуют заново; первое значение выхода соответствует t0. Изменение topology/параметров, неизвестное состояние или чужой контекст — диагностируемый отказ. Произвольный перенос состояния между моделями в этот этап не входит.

## 5. Численное ядро и ресурсы

Собрать разреженную MNA-систему, например `E dx/dt + G x = b(t)`, с явными ограничениями идеальных источников и состояниями накопителей. DC: C разомкнут, L имеет нулевое установившееся падение кроме заданного DCR. AC: комплексные коэффициенты `G + jωE`. Не обращать матрицу явно и не делать dense-путь единственным production solver.

Разделить описание/компиляцию сети, численную сборку, факторизацию/решение, восстановление токов/потерь и сериализацию. Переиспользовать неизменные topology/sparsity; numerical factorization — только когда значения матрицы действительно совпадают. Частота, шаг интегратора, параметры элементов и ограничения источников участвуют в корректной инвалидации. Добавить наблюдаемые счётчики подготовки/решений для тестов, не обещать ускорение без измерения.

Сохранять KCL, residual, баланс мощности для DC/AC в заявленной нормировке, баланс энергии во времени: работа источников = потери + изменение энергии C/L с численным допуском. Не подавлять малые отрицательные/положительные ошибки без отчётности. Вырожденность, несовместимые идеальные источники, неизвестные узлы, неполные mapping и нечисловой результат дают диагностику.

Перед выделением памяти оценивать размер сети/результата, соблюдать существующие лимиты. Проверять отмену между частотами и временными шагами; общий процессный timeout остаётся защитой длительной факторизации. После ошибки следующий анализ в том же публичном runner должен работать; не оставлять дочерних процессов. Не создавать неограниченный кеш или worker, удерживающий все прошлые поля.

## 6. Пример целевого прямого DSL

Это пример **явно заданной** RLC-модели, не результат извлечения PCB. Все номиналы ниже — тестовые предположения. Пример должен стать исполняемым fixture после реализации; он не является уже выполненной проверкой.

```js
const a = analysis();
const circuit = a.circuit({
  nodes: ["gnd", "src", "mid", "load"],
  reference: "gnd",
  ports: [{ id: "output", positive: "load", negative: "gnd" }],
  elements: [
    { id: "V1", kind: "voltage-source", nodes: ["src", "gnd"],
      voltageV: 3.3, model: "ideal" },
    { id: "R1", kind: "resistor", nodes: ["src", "mid"], resistanceOhm: 0.05 },
    { id: "L1", kind: "inductor", nodes: ["mid", "load"],
      inductanceH: 10e-9, seriesResistanceOhm: 0.01 },
    { id: "C1", kind: "capacitor", nodes: ["load", "gnd"],
      capacitanceF: 100e-6, esrOhm: 0.02, eslH: 1e-9 },
    { id: "I1", kind: "current-source", nodes: ["load", "gnd"],
      currentA: 0.1,
      waveform: { kind: "step", from: 0.1, to: 1, atS: 100e-6, riseS: 1e-6 } },
  ],
});
const out = circuit.port("output");

const dc = await a.dc().circuit(circuit).run();
a.check({ name: "DC при 100 mA", actual: dc.voltage(out),
  min: 3.2939, max: 3.2941, unit: "V" });

const ac = await a.pi().circuit(circuit).domain("frequency")
  .frequency({ startHz: 100, stopHz: 1e7, points: 201, scale: "log" }).run();
a.plot({ title: "Выходной импеданс, модуль", data: ac.impedance(out).magnitude() });
a.plot({ title: "Выходной импеданс, фаза", data: ac.impedance(out).phaseDeg() });

const transient = await a.pi().circuit(circuit).domain("time")
  .initial("steady").time({ stopS: 500e-6, sampleStepS: 0.5e-6 }).run();
a.plot({ title: "Напряжение при скачке нагрузки", data: transient.voltage(out) });
a.plot({ title: "Ток индуктивности", data: transient.current("L1") });
a.check({ name: "Заданный бюджет просадки", actual: transient.voltage(out).min(),
  min: 3.0, unit: "V" });

const continued = await a.pi().circuit(circuit).domain("time")
  .initial(transient.finalState).time({ stopS: 1e-3, sampleStepS: 0.5e-6 }).run();
a.plot({ title: "Продолжение на той же временной оси", data: continued.voltage(out) });
```

Здесь рабочая точка имеет аналитический ответ `3.3 - 0.1 × (0.05 + 0.01) = 3.294 V`. Частотные и переходные ожидания выводить из независимых формул/эталонов, а не фиксировать первую выдачу нового solver как истину. Для AC импеданса waveform не является возбуждением; этот режим использует тестовое портовое возбуждение, что должно быть видно в отчёте.

## 7. Результаты и визуализация

- DC `voltage(port)` — V, `current(elementId)` — A, `losses` — суммарная мощность диссипации W. Transient возвращает соответствующие серии; частотный Z — комплексную серию Ohm с осью Hz. Ось времени — s.
- Реализовать необходимые операции комплексных DataValue: real/imaginary/magnitude/phaseDeg. В фазе использовать явно задокументированный диапазон; фаза нулевого значения не должна выдумываться. Для комплексной серии min/max до выбора real/magnitude не определены.
- Графики: модуль Z по логарифмической частоте, фаза, напряжения/токи во времени, сравнение нагрузки/ESR и численного уточнения. Подписи единиц, легенды, одинаковые оси при сравнении, видимые assumptions/validity и status checks.
- У standalone circuit нет геометрической карты потерь/токов платы. `lossMap`/`voltageMap`/`currentDensityMap` не фабриковать. Элементы и узлы показывать таблицей/схемой, пространственные результаты DC платы — прежним способом.
- Неизвестная/частичная величина не превращается в ноль или pass. Провал `a.check` не останавливает дальнейший DSL; audit отличает ожидаемый fail от отказа solver.
- Сериализованные результаты и ссылки должны быть самодостаточны для просмотра текущего запуска. Нельзя подбирать недостающие данные из старого successful run.

## 8. Обязательные тесты

### Независимые численные эталоны

1. R-делитель, разветвлённая R-сеть, несколько источников и ненулевой ток источника с проверкой знака. DC напряжения и токи — относительная ошибка ≤1e-8 либо обоснованный абсолютный floor для нуля.
2. DC-предел C/L, ESR/ESL и DCR; эквивалентность непосредственных R/C/L и `a.model` с mapping.
3. AC RC/RL и последовательный/параллельный RLC с аналитическим комплексным импедансом. Модуль/комплексный ответ ≤1e-6 относительной ошибки вдали от нулей/полюсов; отдельный физический абсолютный floor около нуля. Проверить обе части, а не только красивый модуль.
4. RC-заряд/разряд, RL-ступень, затухающий RLC с аналитическим откликом. При выбранном допуске solver амплитуды/постоянные времени/экстремумы должны сходиться; целевая ошибка ≤0.5% характерной ненулевой шкалы. Не ослаблять критерий, ссылаясь на неточные параметры реальной платы: это синтетический эталон.
5. AC и установившийся transient при синусоидальном возбуждении согласованы по амплитуде и фазе. При сравнении помнить: Z измеряет источник тестового тока, а transient — заданные реальные источники; сравнивать одну и ту же линейную задачу.
6. KCL/residual, DC-мощность и transient-энергия с отдельными физическими допусками. Для временного баланса показать уменьшение ошибки при уточнении; цель ≤0.5% обменённой энергии с floor для почти нулевого возбуждения.
7. Отдельно уменьшить tolerances внутреннего интегратора и отдельно изменить `sampleStepS`. Показать, что грубый вывод не определяет внутреннюю динамику. Если пики получаются только из sampled series, явно указать ограничение наблюдения и проверить достаточно частый вывод для peak-checks.
8. Step/pulse/PWL с событием между точками вывода, короткий конечный фронт, повтор, окончание count и sine-фаза. Нулевой фронт либо обрабатывается корректно, либо неподдержанный импульсный случай отвергается явно.
9. Один длинный transient эквивалентен двум с `finalState`, включая событие после границы продолжения. Изменённые параметры/чужое состояние отклоняются.

### Интеграция и отрицательные случаи

- Production runner и упакованный публичный API, без альтернативного solver в tests/helper.
- Несколько портов/расчётов, позднее объявление наблюдения, неизменность прежних результатов, повтор RHS и корректная инвалидация при изменении R/C/L/частоты/шага.
- Плавающая сеть, несовместимые идеальные источники, вырожденный идеальный LC-контур/ограничения, неизвестный узел/элемент/mapping, неподдержанная модель. Ошибка без скрытых shunt/gmin.
- Budget/timeout/cancel, слишком большой вывод, отказ численного решения и успешный следующий запуск. Никаких NaN/Infinity в JSON.
- Автоматический audit, вызываемый из launcher: идентичность всех случаев, конечность/единицы/оси, критерии эталонов и сходимости, checks и данные графиков. Negative tests намеренно удаляют/портят измерения, оси, units, checks, continuation и quality; audit обязан упасть.
- Сохранить регрессии D1–D3, M1 и исходные guards DC. Не ослаблять их ради нового ядра.

Числа выше — условия приёмки, не обещание заранее выполненного измерения. Если получить их не удаётся, представить воспроизводимый отказ и объяснение; не менять эталон/физическую постановку, чтобы скрыть проблему.

## 9. Реальные платы и отчёты

Добавить минимум три сценария `rlc.js` + тонкий `rlc.ts` в существующих fixtures: **STM32G0_CAN_RS485, USB_PD_Trigger_5A, ThunderF722**. Launcher: `npm run test:pcb-analyze -- <имя> --name rlc`. Существующие `dc.js` сохранить.

Для каждой платы:

1. Выбрать конкретный rail, источник и потребителей по проверенным обозначениям/сетям fixture; сохранить привязку в отчёте. Не выдумывать designator/pin.
2. Показать исходный board DC и рядом явно заданную lumped RLC-модель выбранного участка с нагрузкой во времени. Можно сослаться на воспроизводимый DC данного evidence; для совместного запускa использовать отдельные analysis-контексты.
3. Все R/L/C/ESR/ESL и источники чисел перечислить: явная тестовая гипотеза, известный параметр или ограниченная DC-оценка. Получать R из V/I допустимо только для явно подходящей постановки; это не даёт L/C и не доказывает AC-модель всей платы.
4. Сравнить минимум два заданных режима нагрузки либо ESR; добавить частотный график, transient, checks и численное уточнение хотя бы одного режима. Один намеренно строгий check должен дать fail, следующий check/plot — выполниться.
5. В заголовке отчёта явно написать «заданная RLC-модель участка; частотное извлечение PCB не выполнялось». Board outline может давать контекст, но цветовые AC-карты PCB без извлечённой модели запрещены.

Эти сценарии проверяют полезность DSL на реальных обозначениях и воспроизводимость, **не заменяют** аналитические тесты и не доказывают точность модели конкретной платы. Все восемь прежних DC-плат остаются regression coverage; при изменении их общего runtime/result пути проверить текущей версией, без циклических повторов неизменного прогона.

Для артефактов сохранить исходный `.js`, resolved inputs, версии/hashes реализации и addon, результат, audit, время/пиковую память и HTML/графики. Сгенерированное — в ignored `debugging/`; assertions — в versioned tests. Открыть отчёты и визуально проверить минимум по одному частотному/временному графику и страницу каждой из трёх плат; сохранить скриншоты и перечень реально просмотренного.

## 10. Что не делать

Не реализовывать сейчас извлечение RLGC/PDN из PCB, skin/proximity solver, SI/DDR/eye, thermal, EMI/full-wave, nonlinear SPICE, DC-DC feedback/control/converters, Touchstone, S/Z/Y conversions, `a.connect`, fitting/FFT, автоматический подбор/раскладку decaps, GPU/F32, CAD/export/новый RoutingBoardV2 или поиск моделей в интернете из runtime. Не добавлять ресурсы/зависимости только ради будущих этапов.

Эти части не удаляются из согласованного плана. Остаток P6 (multiport/ресурсы/частотные модели и необходимые преобразования), P7 и P8 получают отдельные задания после приёмки P6a. Не отмечать весь P6 выполненным.

## 11. Порядок и приёмка

Реализовать последовательно внутри этого задания: описание/компиляция сети и DC → комплексный Z → adaptive transient/state → production DSL/result → прямые сценарии и visual audit. На каждом шаге сначала маленький независимый эталон; не начинать с большой платы как единственного оракула.

Этап принят, когда все обязательные режимы доступны через существующий DSL, выполняются перечисленные численные/отрицательные тесты, есть три честно маркированных сценария плат и их отчёты, прежний DC не регрессировал, границы/семантика документированы. Неподдержанные режимы диагностируются, нет заглушек с успешными нулями.

Исполнитель запускает релевантные focused Rust/Node tests, `npm run native:build`, typecheck/build, package checks; тяжёлые corpus runs — один раз на итоговую версию, повтор только после влияющих изменений или неуспешного прогона. Точные команды/exit codes записать в `electrical-network-verification.md`, вместе с допусками, графиками, hashes и оставшимися ограничениями. Обновить `src/analyze/README.md`, `native/analyze/README.md`, `spec-doc.d.ts`, `dsl-reference.md`, индекс experimental docs и CHANGELOG. В итоговом сообщении перечислить изменения, реально выполненные проверки и путь к evidence; передать на ревью без перехода к следующему этапу.
