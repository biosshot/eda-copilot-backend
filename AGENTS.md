# Repository rules

- Before editing, read `CHANGELOG.md` and the relevant module `AGENTS.md`. Search for an existing implementation, helper, or test before adding one (`rg` / `rg --files`); avoid duplicate utilities.
- Keep diffs minimal. Do not refactor neighboring code without a reason tied to the task. Preserve user changes and fixture/DSL inputs unless the task explicitly calls for editing them.
- Main areas: `src/circuit-layout/` places schematics; `src/pcb-layout/` places PCBs; `native/pcb-board-packer/` contains Rust solvers; `src/devices/` resolves library parts and footprints; `src/types/` holds shared contracts; `tests/` contains focused tests and board fixtures; `scripts/` contains development tools. Start at [docs/architecture-map.md](docs/architecture-map.md) for entry points.
- From the repository root: `npm run typecheck` checks TypeScript, `npm run build` builds the package, `npm test` runs unit tests, `npm run test:pcb` selects PCB tests, and `npm run check` runs typecheck/build/tests. There is no separate lint command. For Rust changes, run `npm run native:build` and focused Rust tests.
- After a change, run checks relevant to the touched module and report what ran. Prefer focused tests before broad suites; do not start expensive full-board runs for documentation-only work.
- Update `CHANGELOG.md` under `Unreleased` for meaningful behavior, performance, workflow, or compatibility changes. Record placement experiment evidence under `docs/experimental/pcb/`; keep generated local output under ignored `debugging/`.
- For the CubeCL block-solver task, read [the current roadmap](docs/experimental/pcb/cubecl-backend/ROADMAP.md) before edits and after context compaction. Work in the main backend checkout on `feat/block-solver-cubecl`, not a worktree; scope is block solver and saved FPGA only. Reuse archived fast OpenCL code and validate every representation/math change. Record concrete evidence before checking milestones; ask the user before new architecture, precision, drift, or algorithm tradeoffs.
